# tflm 业务层嵌入架构规划

## 1. 文档定位

本文规划 `tflm` 下一阶段的架构演进方向：

> 让 `tflm` 像 Zephyr 一样成为一个可以被外部业务工程使用的架构树，让机器人业务层以“应用工程”的形式嵌入并使用 `tflm`，而不是把业务代码长期放在框架仓库内部，或者复制一份框架后再进行改造。

本文讨论的是目标架构、边界和迁移路线。

当前仓库仍然是一个“框架能力与参考业务项目放在同一个仓库中的工程”，根目录 `CMakeLists.txt` 仍然承担应用工程入口，`project/` 仍然是当前仓库的项目装配层。本文中的外部业务仓库、Zephyr module、west manifest 和公共注册接口，属于后续规划，需要按阶段落地。

因此本文始终区分三种状态：

| 状态 | 含义 |
| --- | --- |
| 当前实现 | 当前工作区已经存在并正在使用的代码路径 |
| 迁移中 | 可以在现有代码上逐步抽取，不要求一次性重写 |
| 目标架构 | 框架仓库和业务仓库完全分离后的理想形态 |

本文不要求现在立即拆仓库，也不要求当前赛季中断业务开发。正确的策略是先把接口和边界稳定下来，再把业务层逐步移到框架之外。

---

## 2. 一句话目标

最终希望形成下面这种关系：

```text
Zephyr
    -> 提供 RTOS、设备树、内核、驱动基础和构建系统

tflm
    -> 提供嵌入式项目架构、驱动适配、设备模块、算法、topic、调试能力

业务仓库
    -> 选择板卡、实例化模块、组合控制逻辑、编写机器人线程和实验脚本

最终固件
    -> Zephyr + tflm + 某个业务项目
```

再压缩成一条依赖关系：

```text
业务项目依赖 tflm
tflm 依赖 Zephyr
Zephyr 不依赖业务项目
```

最重要的约束是：

```text
业务层可以调用架构层
架构层不能反向包含业务层
```

这就是“让业务层使用架构层”的核心。

## 3. 为什么现在要开始规划

当前 `tflm` 已经具备了明显的框架特征：

- `drivers/` 已经有 UART、CAN、SPI、USB、GPIO、PWM 等硬件访问能力；
- `modules/` 已经有 IMU、Remote、Motor、PowerMeter 等设备能力；
- `algorithm/` 已经有 PID、滤波、姿态、RLS 和推理相关能力；
- `topic/` 已经开始承担跨线程数据契约；
- `cmd/` 已经拥有 Shell、Buzzer、Flash 等运行时辅助能力；
- `project/` 已经负责板级配置、启动、线程装配和整机业务；
- `scripts/` 已经形成了固件与 Python 实验之间的闭环；
- `REGISTER_INIT()`、`.user_init`、`.remote`、`.imu`、`.shell_var` 等注册机制已经把许多中央分发逻辑搬到了编译期；
- IMU 的前后端分离、Remote 的协议注册和双 UART 冗余规划，已经体现出平台化思路。

但当前架构仍然存在一个根本性限制：

```text
tflm 的架构层和某个具体业务项目仍在同一个应用仓库中
```

当前根 `CMakeLists.txt` 仍然直接控制：

- `ACTIVE_PRJ`
- `PROJ_DIR`
- `CONFIG_PRJ_TEST`
- `project/boards/`
- `project/thread/`
- `project/apps/`

这适合当前阶段快速演进，但不适合长期作为开源框架的最终形态。

如果以后每个新机器人都复制一份完整 `tflm`，会出现以下问题：

1. 框架修复需要手动同步到多个业务仓库；
2. 不同项目会逐渐修改同一个框架文件，最后难以区分公共能力和业务特例；
3. `project/` 看起来像框架层的一部分，但实际上承担的是某一台机器人的具体业务；
4. 新用户无法判断哪些目录可以改，哪些目录应该只通过配置使用；
5. 框架版本没有清晰的提交、标签和兼容策略；
6. 开源后，用户只能“复制整个仓库”，不能像使用 Zephyr 一样选择版本并接入自己的应用；
7. 框架的复用价值会被具体机器人业务的文件和配置掩盖。

所以现在需要把目标从：

```text
在一个仓库里继续把框架做大
```

提升为：

```text
把框架变成可被业务工程消费的独立能力集合
```

## 4. 对 Zephyr 使用方式的类比

这里所说的“像使用 Zephyr 树一样”，不是简单地模仿 Zephyr 的目录名字，而是模仿它的使用关系。

### 4.1 Zephyr 的使用关系

一个普通 Zephyr 应用通常拥有自己的：

```text
应用仓库
├── CMakeLists.txt
├── Kconfig
├── prj.conf
├── boards/
├── src/
└── west.yml
```

Zephyr 本身提供：

```text
Zephyr 仓库
├── kernel/
├── subsys/
├── drivers/
├── include/
└── CMake/Kconfig/设备树基础设施
```

应用不会把自己的业务线程写进 Zephyr 的内核目录，也不会为了增加一个机器人功能而修改 Zephyr 的 `main()`。

应用通过：

```text
CMakeLists.txt
Kconfig
prj.conf
devicetree
west.yml
```

把 Zephyr 组织成自己的固件。

### 4.2 tflm 的对应关系

目标状态下：

```text
Zephyr 的 kernel/subsys/drivers
    对应
tflm 的 drivers/modules/algorithm/topic/cmd

Zephyr 应用的 src/boards/prj.conf
    对应
业务项目的 app/boards/prj.conf

Zephyr 的 west manifest
    对应
业务项目对 tflm 版本的声明
```

目标关系可以画成：

```text
业务项目仓库
    ├── app/
    ├── boards/
    ├── scripts/
    ├── CMakeLists.txt
    ├── Kconfig
    ├── prj.conf
    └── west.yml
             │
             │ west update / Zephyr module discovery
             ▼
tflm framework
    ├── drivers/
    ├── modules/
    ├── algorithm/
    ├── topic/
    ├── cmd/
    └── zephyr/
             │
             ▼
Zephyr
```

业务项目通过 `west.yml` 固定某个 tflm 版本，通过 Kconfig 选择能力，通过 CMake 把业务源码加入最终 `app` 目标，通过 devicetree 描述板级硬件。

### 4.3 “嵌入”到底是什么意思

业务层嵌入架构层，不意味着业务层在运行时作为一个动态插件加载。

嵌入发生在三个阶段：

#### 编译期嵌入

```text
业务 Kconfig
    -> 选择 tflm 功能

业务 CMake
    -> 加入业务源码

tflm CMake
    -> 加入被选择的框架源码

最终
    -> 统一链接为一个 Zephyr 固件
```

#### 链接期嵌入

```text
业务线程中的 REGISTER_INIT()
业务协议中的 REGISTER_REMOTE()
业务电机中的 CAN_RX_HANDLER()
调试变量中的 REGISTER_SHELL_VAR()
    -> 进入框架规定的链接段
    -> 链接器生成统一注册表
```

#### 运行期嵌入

```text
业务项目调用 tflm 公共接口
    -> tflm 驱动访问硬件
    -> tflm 模块维护设备能力
    -> tflm topic 传输数据
    -> 业务线程完成具体控制
```

因此，“业务层嵌入架构层”的真实含义是：

> 业务仓库使用框架提供的构建入口、配置入口、公共头文件、注册协议和运行时能力，最终与框架一起生成一个完整固件。

## 5. 当前架构与目标架构

### 5.1 当前结构

当前仓库大致是：

```text
tflm/
├── CMakeLists.txt            # 当前同时承担应用入口和框架装配
├── Kconfig                   # 当前应用入口
├── prj.conf                  # 当前默认项目配置
├── src/
│   └── main.c
├── drivers/                  # 框架层
├── modules/                  # 框架层
├── algorithm/                # 框架层
├── topic/                    # 框架层
├── cmd/                      # 框架层辅助能力
├── project/                  # 当前项目装配和业务
│   ├── apps/
│   ├── boards/
│   └── thread/
├── scripts/                  # 主机侧实验脚本
└── doc/
```

当前关系是：

```text
根应用 CMake
    -> add_subdirectory(drivers)
    -> add_subdirectory(algorithm)
    -> add_subdirectory(modules)
    -> add_subdirectory(topic)
    -> add_subdirectory(cmd)
    -> add_subdirectory(project)
```

这套结构在开发阶段很有效：

- 框架代码和实验代码在同一处；
- 修改后可以快速构建；
- `project/thread/test/` 可以直接验证新设备；
- `project/boards/` 可以快速切换板卡；
- 所有代码都在同一个 IDE 工程中，追踪调用关系很方便。

但它更像：

```text
一个包含完整框架和参考业务的超级工程
```

还不是：

```text
一个被外部业务仓库消费的框架模块
```

### 5.2 目标框架仓库

目标状态下，tflm 框架仓库可以变成：

```text
tflm/
├── zephyr/
│   ├── module.yml
│   ├── CMakeLists.txt
│   └── Kconfig
├── include/
│   └── tflm/
│       ├── init/
│       ├── irq/
│       ├── registration/
│       └── version.hpp
├── drivers/
├── modules/
├── algorithm/
├── topic/
├── cmd/
├── scripts/
│   ├── common/
│   └── validation/
├── examples/
│   ├── minimal/
│   └── reference_robot/
├── doc/
├── CMakeLists.txt             # 可选：兼容独立参考构建
└── Kconfig                   # 可选：兼容当前单仓库构建
```

其中最重要的是：

```text
zephyr/module.yml
zephyr/CMakeLists.txt
zephyr/Kconfig
```

这三个文件负责让 tflm 作为 Zephyr module 进入外部业务工程。

框架仓库不再把某个具体机器人 `project/` 当成唯一业务入口。

### 5.3 目标业务仓库

一个具体机器人业务仓库可以是：

```text
robot-sentry/
├── CMakeLists.txt
├── Kconfig
├── prj.conf
├── west.yml
├── app/
│   ├── main.c
│   ├── apps/
│   │   ├── init_entry.cpp
│   │   ├── irq_handlers.cpp
│   │   └── system_policy.cpp
│   ├── thread/
│   │   ├── can/
│   │   ├── remote/
│   │   ├── imu/
│   │   ├── chassis/
│   │   ├── gimbal/
│   │   └── test/
│   ├── topic/
│   │   └── robot_state/
│   └── config/
├── boards/
│   ├── hpm/
│   │   └── hpm5361icb/
│   └── st/
├── scripts/
│   ├── bringup/
│   ├── tuning/
│   └── analysis/
└── doc/
```

业务仓库只回答当前机器人自己的问题：

- 当前机器人使用哪块板；
- 当前板卡的 UART、CAN、SPI 和 PWM 连接在哪里；
- 当前机器人需要哪些线程；
- 哪些模块属于底盘，哪些模块属于云台；
- 当前控制周期、优先级和参数是什么；
- 当前业务状态如何组织；
- 当前实验如何采集、回放和评估。

业务仓库不应该重新实现：

- UART DMA；
- SPI 同步收发；
- CAN 驱动访问；
- IMU 设备管理公共接口；
- Remote 协议解析公共逻辑；
- PID、滤波、RLS 等公共算法；
- Shell 的变量注册机制；
- 初始化链接段收集机制。

## 6. 目标依赖方向

### 6.1 框架层依赖关系

目标框架层保持：

```text
Zephyr
    ↓
drivers
    ↓
modules
    ↓
algorithm / topic
    ↓
业务项目
```

实际关系并不要求严格成为一条直线，但必须满足“依赖方向向下或向公共契约收敛”。

更完整地表示：

```text
Zephyr / devicetree / kernel API
                 │
                 ▼
             drivers
          ┌──────┼──────┐
          ▼      ▼      ▼
      modules algorithm topic
          │      │      │
          └──────┼──────┘
                 ▼
            business app
```

`cmd/` 是横切能力，不完全位于传统的上下层关系中：

```text
cmd/
    -> 可以依赖 drivers
    -> 可以被 modules 使用
    -> 可以被业务线程调用
    -> 不拥有具体机器人控制策略
```

### 6.2 业务层依赖规则

业务项目可以：

- 包含 tflm 公共头文件；
- 声明 tflm 驱动对象；
- 实例化 tflm 设备模块；
- 使用 tflm 算法；
- 发布和订阅 tflm topic；
- 使用 `REGISTER_INIT()`；
- 使用 `CAN_RX_HANDLER()`；
- 使用 `REGISTER_SHELL_VAR()`；
- 在自己的线程中组合多个模块；
- 为自己的设备和业务定义新 topic；
- 为自己的项目增加私有算法。

业务项目不应该：

- 修改 tflm 的内部源文件来适应一台机器人；
- 直接依赖 tflm 的内部私有成员；
- 把业务策略写进 drivers；
- 让 modules 直接包含业务线程；
- 让 framework CMake 反向搜索业务仓库；
- 让 tflm 依赖某个具体机器人名称；
- 通过修改链接脚本手工补框架注册项；
- 把所有项目配置都塞进 tflm 的公共 Kconfig。

### 6.3 框架层不能反向依赖业务层

这是整个规划中最重要的禁令：

```text
drivers/modules/algorithm/topic/cmd
    不得 include app/thread/robot-specific headers
```

例如，下面的写法应该被禁止：

```cpp
// 错误示例
#include "trd_chassis.hpp"
#include "sentry_config.hpp"
#include "robot_state.hpp"

namespace tflm::motor
{
    void DjiC620::UpdateForSentry(...)
    {
        // 将某台机器人的业务判断塞入通用电机模块
    }
}
```

正确的方向是：

```text
Motor module
    -> 提供反馈快照、状态、打包接口

Chassis thread
    -> 决定如何使用这些反馈
```

当前 `Motor`、`PowerMeter` 没有独立线程的设计，正好适合作为这种边界的示例。

## 7. 框架模块化接入方案

### 7.1 为什么采用 Zephyr module

目标不是再造一套包管理器，而是直接使用 Zephyr 已经提供的外部模块模型。

使用 Zephyr module 的好处：

1. tflm 可以拥有独立 Git 仓库；
2. 业务项目可以通过 west 固定 tflm 版本；
3. tflm 的 CMake 和 Kconfig 可以自动进入 Zephyr 构建系统；
4. 不同业务项目可以使用不同 tflm 版本；
5. 用户可以用本地路径覆盖远程模块进行开发；
6. 框架和业务的提交历史可以独立；
7. tflm 不需要把所有业务代码放进自己的根 CMake；
8. 开源后用户可以像使用其他 Zephyr 外部模块一样接入。

Zephyr 的模块机制要求模块仓库提供 `zephyr/module.yml`，并通过模块中的 CMake/Kconfig 文件参与构建。模块可以由 west 工作区发现，也可以通过 CMake 的模块路径显式加入。正式迁移时应以当前使用的 Zephyr 版本文档和实际构建结果为准。

### 7.2 初始 module.yml

目标形式可以是：

```yaml
name: tflm

build:
  cmake: zephyr
  kconfig: zephyr/Kconfig
```

这里的具体文件路径可以在迁移阶段调整，但必须满足一个原则：

```text
模块描述文件只负责告诉 Zephyr：
框架的 CMake 和 Kconfig 在哪里
```

模块描述文件不应该写入：

- 某个业务项目的板卡；
- 某个机器人的默认线程；
- 某个比赛的 CAN ID；
- 某个业务仓库的绝对路径；
- 某个本地电脑的 SDK 路径。

### 7.3 框架模块 CMake

目标 `zephyr/CMakeLists.txt` 负责把 tflm 的可选能力加入 Zephyr 的 `app` 目标。

示意结构：

```cmake
set(TFLM_ROOT ${ZEPHYR_TFLM_MODULE_DIR})

if(CONFIG_TFLM)
    add_subdirectory(
        ${TFLM_ROOT}/drivers
        ${CMAKE_CURRENT_BINARY_DIR}/tflm/drivers
    )

    add_subdirectory(
        ${TFLM_ROOT}/algorithm
        ${CMAKE_CURRENT_BINARY_DIR}/tflm/algorithm
    )

    add_subdirectory(
        ${TFLM_ROOT}/modules
        ${CMAKE_CURRENT_BINARY_DIR}/tflm/modules
    )

    add_subdirectory(
        ${TFLM_ROOT}/topic
        ${CMAKE_CURRENT_BINARY_DIR}/tflm/topic
    )

    add_subdirectory(
        ${TFLM_ROOT}/cmd
        ${CMAKE_CURRENT_BINARY_DIR}/tflm/cmd
    )

    target_include_directories(app PRIVATE
        ${TFLM_ROOT}/include
    )

    zephyr_linker_sources(
        ROM_SECTIONS
        ${TFLM_ROOT}/cmd/linker/tflm_init.ld
    )
endif()
```

这段代码只是目标示意，真正落地时需要结合 Zephyr 当前 module CMake 的调用上下文验证：

- `add_subdirectory()` 的源码目录和二进制目录；
- 各层 `CMakeLists.txt` 使用的 `CMAKE_CURRENT_SOURCE_DIR`；
- linker script 的加入时机；
- 是否需要把公共头文件目录改为 `include/tflm/`；
- 是否需要给每个框架子目录增加独立的 CMake 包装层。

### 7.4 框架模块 Kconfig

目标 `zephyr/Kconfig` 负责把 tflm 的能力菜单加入 Zephyr 的 Kconfig 树：

```kconfig
menuconfig TFLM
    bool "Enable tflm framework"
    default y
    help
      Enable the tflm embedded architecture framework.

if TFLM

rsource "../drivers/Kconfig"
rsource "../algorithm/Kconfig"
rsource "../modules/Kconfig"
rsource "../topic/Kconfig"
rsource "../cmd/Kconfig"

endif
```

迁移阶段需要重新检查 Kconfig 路径相对于 `zephyr/Kconfig` 的解析方式，不应直接假定当前根 `Kconfig` 的相对路径在 module 模式下完全不变。

### 7.5 框架能力与业务选择分离

框架 Kconfig 只声明能力：

```text
TFLM_COM_UART_DMA
TFLM_COM_SPI
TFLM_MOD_DEV_IMU
TFLM_MOD_DEV_REMOTE
TFLM_FLT_QUATERNION
TFLM_CMD_SHELL_VAR
```

业务 Kconfig 决定使用哪些能力：

```text
APP_REMOTE
    -> select TFLM_MOD_DEV_REMOTE
    -> select TFLM_MOD_DEV_REMOTE_AUTO

APP_IMU
    -> select TFLM_MOD_DEV_IMU
    -> select TFLM_MOD_DEV_IMU_ICM42688P
    -> select TFLM_TPC_IMU_TO

APP_SHELL
    -> select TFLM_CMD_SHELL_VAR
```

当前符号大多是 `COM_*`、`MOD_*`、`TPC_*`、`CMD_*` 形式。迁移时可以采用两种策略：

#### 策略 A：保留现有符号

优点：

- 修改范围小；
- 现有业务配置可以继续使用；
- 迁移速度快。

缺点：

- 开源后容易和其他 Zephyr 模块的符号冲突；
- 用户无法从名字看出符号属于 tflm；
- 长期维护时命名空间不够清晰。

#### 策略 B：增加 TFLM 前缀

例如：

```text
TFLM_COM_UART_DMA
TFLM_MOD_DEV_IMU
TFLM_MOD_DEV_REMOTE
TFLM_CTL_PID
TFLM_TPC_REMOTE_TO
TFLM_CMD_SHELL_VAR
```

优点：

- 公共接口的归属清楚；
- 更适合独立开源模块；
- 减少与 Zephyr 或其他模块的命名冲突。

缺点：

- 需要修改大量 Kconfig、CMake 和文档；
- 需要提供过渡兼容；
- 当前业务配置文件会有较大改动。

建议采用：

```text
第一阶段保留现有符号，先完成 module 化
第二阶段新增 TFLM 前缀符号
第三阶段提供旧符号兼容映射
第四阶段删除旧符号
```

不要在 module 化和命名空间迁移两个高风险动作上同时进行大规模重构。

## 8. 业务仓库如何使用 tflm

### 8.1 业务仓库根 CMake

目标业务仓库的根 `CMakeLists.txt` 应该只负责：

1. 声明这是一个 Zephyr 应用；
2. 提供业务自己的源码；
3. 加入业务自己的 board root；
4. 选择业务自己的 Kconfig 和配置；
5. 加入业务线程和应用装配。

示意：

```cmake
cmake_minimum_required(VERSION 3.20.0)

list(APPEND BOARD_ROOT
    ${CMAKE_CURRENT_SOURCE_DIR}/boards
)

find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})
project(robot_sentry)

target_sources(app PRIVATE
    app/main.c
    app/apps/init_entry.cpp
    app/apps/irq_handlers.cpp
)

target_include_directories(app PRIVATE
    ${CMAKE_CURRENT_SOURCE_DIR}/app
)

add_subdirectory(app)
```

业务 CMake 不应该复制 tflm 的：

```cmake
add_subdirectory(drivers)
add_subdirectory(algorithm)
add_subdirectory(modules)
add_subdirectory(topic)
add_subdirectory(cmd)
```

因为这些目录应该由 tflm module 自动进入 Zephyr 构建系统。

业务 CMake 只需要加入自己的：

```text
app/
```

### 8.2 业务仓库 Kconfig

业务 Kconfig 负责声明当前机器人有哪些功能：

```kconfig
menuconfig APP_ROBOT
    bool "Robot application"
    default y

if APP_ROBOT

config APP_REMOTE
    bool "Remote receiver"
    default y
    select MOD_DEV_REMOTE
    select MOD_DEV_REMOTE_AUTO
    select TPC_REMOTE_TO

config APP_IMU
    bool "IMU"
    default y
    select MOD_DEV_IMU
    select MOD_DEV_IMU_ICM42688P
    select TPC_IMU_TO

config APP_CHASSIS
    bool "Chassis control"
    default n
    select MOD_DEV_MOTOR_DJI
    select MOD_CTL_POWER
    select TPC_REMOTE_TO
    select TPC_TO_CAN_TX

endif
```

业务 Kconfig 应该表达：

```text
我需要什么能力
```

而不是重新描述：

```text
UART DMA 的内部缓冲区如何实现
IMU 的内部状态机如何实现
Remote 的协议注册表如何遍历
```

### 8.3 业务线程 CMake

业务线程由业务仓库自己加入：

```cmake
if(CONFIG_APP_REMOTE)
    target_sources(app PRIVATE
        ${CMAKE_CURRENT_SOURCE_DIR}/thread/remote/trd_remote.cpp
    )
    target_include_directories(app PRIVATE
        ${CMAKE_CURRENT_SOURCE_DIR}/thread/remote
    )
endif()

if(CONFIG_APP_IMU)
    target_sources(app PRIVATE
        ${CMAKE_CURRENT_SOURCE_DIR}/thread/imu/trd_imu.cpp
    )
    target_include_directories(app PRIVATE
        ${CMAKE_CURRENT_SOURCE_DIR}/thread/imu
    )
endif()
```

业务线程可以直接调用 tflm 提供的类：

```cpp
#include <tflm/imu/imu.hpp>
#include <tflm/stream/uart.hpp>
#include <tflm/init/entry.hpp>

namespace app::imu
{

static imu::ImuManager imu {};

bool thread_init()
{
    return imu.Init(imu::CalibMode::Auto);
}

bool thread_start()
{
    return imu.Start(ThreadPrio::High);
}

REGISTER_INIT(thread_init, EarlyInit, High, "app_imu_init");
REGISTER_INIT(thread_start, EarlyThread, High, "app_imu_start");

}
```

这里的关键不是示例中的具体命名，而是：

```text
业务线程拥有模块实例和业务周期
tflm 只提供模块能力和公共接口
```

### 8.4 业务配置通过 devicetree 传入

业务仓库应该在自己的板级目录中描述硬件：

```text
boards/
└── hpm/
    └── hpm5361icb/
        ├── hpm5361icb.overlay
        ├── hpm5361icb.conf
        └── board.cmake
```

业务代码只使用 alias：

```text
remote-uart
imu-spi
imu-pwm
user-can1
buzzer-pwm
pc-usb
```

业务模块不应该把下面的信息写死：

```cpp
UART4
SPI2
CAN1
GPIOB pin 15
```

正确关系是：

```text
业务 board overlay
    -> 提供 alias 和设备节点

tflm 驱动
    -> 读取设备树配置

业务线程
    -> 选择 alias 对应的设备并实例化模块
```

这样换板卡时，可以只替换业务仓库里的 board 配置和少量装配代码。

## 9. `project/` 层的重新定义

### 9.1 当前 `project/` 是什么

当前 `project/` 包含：

```text
project/
├── apps/
├── boards/
└── thread/
```

它同时承担：

- 当前项目入口；
- 当前板卡配置；
- 当前线程；
- 当前启动编排；
- 当前中断绑定；
- 当前 Demo；
- 当前整机业务。

所以当前 `project/` 不是纯粹的框架层，也不是纯粹的业务层，而是一个“内置业务项目单元”。

### 9.2 目标 `project/` 应该是什么

在目标架构中，`project/` 不应该被理解为：

```text
tflm 框架内部不可替换的固定目录
```

而应该被理解为：

```text
一个使用 tflm 的业务项目接口约定
```

可以保留 `project/` 这个名字，也可以在外部仓库改成 `app/`。真正重要的是其中的职责：

```text
apps/
    -> 业务应用启动和系统策略

boards/
    -> 业务板级硬件绑定

thread/
    -> 业务线程和多模块控制逻辑
```

换句话说：

```text
project/ 不是被框架“调用”的文件夹
project/ 是被编译系统嵌入到框架中的业务单元
```

### 9.3 业务层嵌入但不污染框架

业务层嵌入框架时，最终固件的编译关系是：

```text
业务 CMake
    -> 加入业务线程

tflm module CMake
    -> 加入框架能力

Zephyr build system
    -> 统一处理 Kconfig、DTS、链接和固件生成
```

在这个过程中，业务源码和框架源码会被链接到同一个 `app` 目标，但文件边界仍然清晰：

```text
同一个固件
不等于
同一个职责层
```

这是“项目层嵌入架构”的正确理解。

## 10. 初始化注册机制的公共化

### 10.1 当前机制

当前初始化机制大致是：

```text
project/apps/Init_entry.hpp
    -> 定义 InitStage、InitLevel、InitEntry、REGISTER_INIT

cmd/linker/tflm_init.ld
    -> 定义 .user_init 段和 start/end 符号

project/apps/Init_entry.cpp
    -> 遍历 __user_init_start 到 __user_init_end
    -> 按阶段执行初始化函数
```

各个线程在自己的 `.cpp` 中声明：

```cpp
REGISTER_INIT(thread_init, MidInit, Mid, "chassis_init");
REGISTER_INIT(thread_start, MidThread, Mid, "chassis_start");
```

这个设计已经实现了：

- 初始化实现和注册信息放在同一个文件；
- 新增线程不需要修改中央初始化表；
- Kconfig 未启用时，对应源文件不进入镜像；
- 链接器自动收集已编译的注册项；
- 业务模块可以本地声明自己的初始化阶段。

### 10.2 当前限制

当前 `REGISTER_INIT` 主要位于：

```text
project/apps/Init_entry.hpp
```

这意味着外部业务仓库如果想使用这个宏，需要：

- 复制 `Init_entry.hpp`；
- 复制 `Init_entry.cpp`；
- 复制链接脚本；
- 自己修正 include 路径；
- 自己处理 `buzzer.hpp`、日志和启动策略的耦合。

这会让公共机制看起来像某个项目的私有实现。

### 10.3 目标拆分

初始化系统应该拆成三部分：

```text
公共注册协议
    -> tflm framework

公共链接段
    -> tflm framework

启动策略和失败策略
    -> 业务项目，或 tflm 提供默认实现
```

#### 框架提供

```text
InitStage
InitLevel
InitFunc
InitEntry
REGISTER_INIT()
.user_init
__user_init_start
__user_init_end
```

#### 业务项目决定

```text
每个业务组件放在哪个阶段
初始化失败是否停机
启动阶段之间是否延时
是否用 Buzzer 提示
是否打印详细日志
是否在启动阶段执行板卡自检
```

目标公共头文件可以放在：

```text
include/tflm/init/init_entry.hpp
```

或者：

```text
include/tflm/registration/init.hpp
```

具体命名可以后续统一，但必须满足：

```text
业务项目只 include 公共接口
不需要复制框架内部实现
```

### 10.4 默认启动器与可替换策略

可以提供两种使用方式。

#### 默认启动器

适合普通业务项目：

```cpp
#include <tflm/init/startup.hpp>

int main(void)
{
    tflm::SystemStartup();
    return 0;
}
```

默认启动器负责：

- 按固定阶段遍历注册表；
- 调用初始化函数；
- 处理 `High/Mid/Low` 失败等级；
- 输出初始化日志；
- 提供基础的阶段统计。

#### 自定义启动器

适合有特殊启动流程的业务：

```cpp
#include <tflm/init/registry.hpp>

int main(void)
{
    tflm::RunStage(InitStage::PreInit);
    BoardSelfCheck();
    tflm::RunStage(InitStage::PreThread);
    tflm::RunStage(InitStage::AppInit);
    return 0;
}
```

这样既保留框架的注册机制，又不强迫所有业务使用完全相同的启动策略。

### 10.5 初始化阶段应该如何稳定

当前阶段：

```text
PreInit
PreThread
EarlyInit
EarlyThread
MidInit
MidThread
LateInit
LateThread
AppInit
AppThread
```

这套阶段可以继续保留，但要明确其语义：

| 阶段 | 适合内容 |
| --- | --- |
| `PreInit` | 底层总线、基础外设、调试控制台、必须先初始化的设备 |
| `PreThread` | 依赖底层外设的早期基础线程 |
| `EarlyInit` | IMU、Remote 等核心数据源的对象初始化 |
| `EarlyThread` | 核心数据源线程启动 |
| `MidInit` | 底盘、云台等控制模块初始化 |
| `MidThread` | 控制线程启动 |
| `LateInit` | PC、USB、日志扩展、非关键外设 |
| `LateThread` | 辅助通信和后台任务 |
| `AppInit` | 业务状态机、实验功能、推理模型 |
| `AppThread` | 业务应用线程 |

但阶段只能表达粗粒度顺序，不能替代所有依赖关系。

后续需要增加：

- 依赖缺失检查；
- 重复注册检查；
- 同名注册检查；
- 初始化耗时统计；
- 初始化状态查询；
- 线程启动前的 ready 检查；
- 失败项和继续运行项的清晰日志。

不要把所有顺序都继续堆进枚举，否则阶段会逐渐变成另一种中央配置表。

## 11. 中断注册机制的公共化

### 11.1 当前机制

当前 CAN 中断分发机制位于：

```text
project/apps/Irq_handlers.h
project/apps/Irq_handlers.cpp
```

注册宏：

```cpp
CAN_RX_HANDLER(USER_RX_CAN1, 0x201, handler, motor1);
```

会把 `CanRxEntry` 放进：

```text
.can_rx1
.can_rx2
.can_rx3
```

中断回调再遍历对应链接段：

```text
CAN IRQ callback
    -> user_can1_rx_callback()
    -> dispatch()
    -> 根据 CAN ID 找到 handler
```

### 11.2 当前限制

当前中断分发基础设施属于 `project/apps/`，因此它看起来像当前业务项目专用代码。

但实际上，下面这部分是可以公共化的：

```text
CanRxEntry
CAN_RX_HANDLER
section 命名规则
start/end 符号
通用 dispatch
```

下面这部分仍然应该由业务项目负责：

```text
哪块 CAN 控制器对应哪个 alias
哪一个业务实例使用哪个 CAN ID
是否在回调里调用 Motor
是否需要滤波、队列或时间戳
板卡的 CAN 中断绑定
```

### 11.3 目标拆分

框架提供：

```text
include/tflm/irq/can_registry.hpp
include/tflm/irq/can_dispatch.hpp
cmd/linker/tflm_init.ld
```

业务项目提供：

```text
app/apps/irq_handlers.cpp
```

业务项目只需要把 Zephyr CAN 回调接到框架 dispatcher：

```cpp
void user_can1_rx_callback(struct can_frame& frame, void*)
{
    tflm::can::Dispatch(
        tflm::can::Bus::UserCan1,
        frame
    );
}
```

具体设备注册仍然在业务项目中：

```cpp
CAN_RX_HANDLER(
    USER_RX_CAN1,
    0x201,
    [](uint8_t* data)
    {
        chassis_motor_1.CanCpltRxCallback(data);
    },
    chassis_motor_1
);
```

这样可以实现：

```text
框架提供通用分发机制
业务提供实际 CAN ID 到对象的映射
```

### 11.4 中断上下文的边界

公共 CAN dispatcher 必须明确：

- 是否运行在 ISR 上下文；
- handler 是否允许调用阻塞 API；
- handler 是否只能更新无锁状态；
- handler 是否允许发布 zbus；
- handler 是否允许调用日志；
- handler 的最大执行时间；
- handler 是否可以嵌套或重入；
- handler 是否需要把数据转移到线程。

建议默认规则：

```text
CAN RX handler 只做：
    解包
    更新设备快照
    写入无锁/短临界区状态
    必要时投递轻量事件

CAN RX handler 不做：
    阻塞
    长时间滤波
    复杂运动学
    电机控制策略
    Flash 写入
    大量日志输出
```

这与当前 Motor、PowerMeter 的被动设备设计一致：

```text
中断更新快照
project/thread 消费快照
```

## 12. 设备模块的外部使用方式

### 12.1 IMU

目标业务项目新增 IMU 时，应主要完成：

```text
board overlay
    -> 提供 imu-spi / imu-pwm alias

modules/imu/devices/<device>
    -> 如果设备是框架尚未支持的新型号，则加入 tflm

app/thread/imu
    -> 选择并启动 ImuManager
```

如果设备驱动已经在 tflm 中，业务项目不应该复制一份 IMU 设备实现。

目标使用方式：

```cpp
static imu::ImuManager imu {};

bool thread_init()
{
    return imu.Init(imu::CalibMode::Auto);
}

bool thread_start()
{
    return imu.Start(ThreadPrio::High);
}
```

IMU 的 SPI 仍然应该由具体设备子类私有持有：

```text
公共 Source/CalibSource
    -> 统一采样、校准和输出接口

Icm42688p/Bmi088
    -> 私有 SPI 对象和芯片寄存器协议
```

业务项目只选择设备，不接触具体 SPI 寄存器协议。

### 12.2 Remote

目标业务项目可以像使用一个数据源模块一样使用 Remote：

```text
board overlay
    -> remote-uart alias 或 remote-uart-0/1 alias

app/thread/remote
    -> 创建 UartDma
    -> 配置 Remote
    -> 启动 Remote

modules/remotes
    -> 协议探测、解析、状态机、超时和 topic 发布
```

协议新增时，原则上只修改 tflm：

```text
modules/remotes/<protocol>/
    -> RemoteProtocol
    -> Validate()
    -> Decode()
    -> REGISTER_REMOTE()
```

业务线程不直接解释 DR16、SBUS、VT12 或 VT13 的帧结构。

双 UART 规划也应保持这个边界：

```text
业务项目决定：
    两个 UART 分别绑定哪两个 alias

Remote 模块决定：
    探测、锁定、超时、切换、残留 FIFO 清理
```

当前双 UART 仍属于规划状态，正式落地时必须保留：

- 热路径 `Read -> Decode -> Publish`；
- 冷路径切换；
- `detect_[2]` 独立状态；
- 切换事务原子性；
- stale FIFO 清理；
- anti-flap 冷却；
- 当前实现与规划状态的文档区分。

### 12.3 Motor 和 PowerMeter

业务项目负责：

- 声明电机实例；
- 配置 CAN 总线；
- 配置 CAN ID；
- 注册接收回调；
- 在底盘或云台线程中读取快照；
- 在 CAN TX 线程中决定发送时机。

tflm 模块负责：

- 反馈帧解析；
- 电机状态计算；
- seqlock 快照；
- 功率测量数据；
- 控制帧打包。

不应该因为业务仓库换了一个机器人，就把电机模块复制到业务仓库。

### 12.4 cmd

`cmd/` 是跨层辅助能力，外部业务项目可以直接使用：

```cpp
#include <tflm/cmd/shell.hpp>

static float chassis_gain = 1.0f;
REGISTER_SHELL_VAR("chassis_gain", chassis_gain);
```

业务项目不需要自己创建调参线程，也不需要把参数手动加入中央调试列表。

`cmd` 的执行宏继续保持：

```text
头文件可常包含
实现由 Kconfig/CMake 决定
功能关闭时提供空操作、false 或错误停机语义
```

这样业务代码可以保持稳定：

```cpp
EXEC_BUZZER_SHORT();
bool ok = EXEC_FLASH_READ(...);
```

而不需要在业务层到处写：

```cpp
#ifdef CONFIG_CMD_BUZZER
...
#endif
```

## 13. Topic 的框架化与业务化

### 13.1 框架 topic

框架可以提供跨项目稳定的数据契约：

```text
topic/remote_to
topic/imu_to
topic/to_can_tx
```

这些 topic 的特点是：

- 不绑定某台机器人；
- 语义足够通用；
- 可以被多个业务项目复用；
- 消费者和生产者边界清晰；
- 版本变化有明确迁移方式。

### 13.2 业务 topic

下面这些内容通常应该由业务仓库拥有：

```text
topic/robot_state
topic/sentry_command
topic/auto_aim_status
topic/chassis_mode
topic/gimbal_mode
topic/referee_policy
```

因为它们描述的是某台机器人的业务语义。

业务 topic 可以放在：

```text
app/topic/
```

或者：

```text
app/contract/
```

不要为了保持目录形式统一，把所有业务 topic 都强行放进 tflm。

### 13.3 判断 topic 属于谁

可以用三个问题判断：

1. 没有这台具体机器人时，这个消息是否仍然有意义？
2. 换一台机器人后，消息字段和语义是否仍然稳定？
3. 这个消息是否描述设备通用能力，还是描述业务状态机？

如果答案偏向通用能力，放入 tflm。

如果答案偏向具体业务，放入业务仓库。

### 13.4 Topic 版本策略

外部业务使用 tflm 后，topic 就不再只是本地文件，而是公共契约。

需要定义：

- 消息版本；
- 单位；
- 时间戳来源；
- 生产者；
- 消费者；
- 超时语义；
- 是否允许覆盖；
- 是否使用 zbus；
- 是否使用 `k_msgq`；
- 字段增加是否兼容；
- 字段删除如何迁移。

建议：

```text
公共 topic：
    变化谨慎，优先增加字段，避免重命名

业务 topic：
    业务仓库自行演进

实验 topic：
    允许快速变化，但不承诺长期兼容
```

## 14. `scripts/` 的归属规划

### 14.1 当前 scripts 的价值

当前 `scripts/` 已经不只是零散脚本，而是固件开发闭环的一部分：

```text
固件输出日志
    -> Python 解析
    -> 数据清洗
    -> 参数拟合
    -> 回放
    -> 生成结论
```

它可以支持：

- IMU 加热辨识；
- UART 性能测试；
- PID 参数搜索；
- 传感器数据回放；
- 控制器离线验证；
- 实验数据可视化。

### 14.2 目标拆分

脚本分成两类：

#### 框架脚本

放在 tflm：

```text
scripts/
├── common/
├── protocol/
├── validation/
└── examples/
```

负责：

- 通用串口读取；
- 通用日志解析；
- 通用数据格式；
- 固件通信协议辅助；
- 框架模块的离线验证；
- 标准实验报告输出。

#### 业务脚本

放在业务仓库：

```text
robot-sentry/scripts/
├── tuning/
├── identification/
├── replay/
├── plot/
└── reports/
```

负责：

- 当前机器人参数；
- 当前电机和底盘模型；
- 当前比赛模式；
- 当前传感器安装方向；
- 当前实验数据；
- 当前业务评估指标。

### 14.3 Python 不能替代固件安全逻辑

Python 可以负责：

- 采集；
- 回放；
- 拟合；
- 统计；
- 画图；
- 参数搜索；
- 生成报告。

Python 不应该替代固件中的：

- 电机失控保护；
- 超温保护；
- 失联保护；
- 输出限幅；
- 急停；
- 关键状态机；
- 实时控制闭环。

目标架构是：

```text
固件负责实时和安全
Python 负责实验和分析
```

这使业务层可以拥有自己的实验流程，同时不会让主机脚本成为固件运行的必要条件。

### 14.4 脚本版本与固件版本

外部业务仓库使用 tflm 后，需要记录：

```text
tflm commit/tag
Zephyr commit/tag
板卡版本
固件配置
Python 依赖版本
实验数据版本
```

每次实验输出建议包含：

```text
framework_version
firmware_git
board
config
script
script_version
timestamp
```

否则同一个 Python 脚本在不同固件协议上运行，很容易造成难以复现的结论。

## 15. 公共头文件和私有头文件

### 15.1 当前问题

当前各层的 CMake 主要把目录直接加入：

```cmake
target_include_directories(app PRIVATE ...)
```

这在单仓库中很方便，但外部业务使用时容易出现：

- 业务代码 include 内部目录；
- 私有实现意外变成公共接口；
- 头文件路径依赖当前目录；
- 改目录名会导致大量业务工程同时失效；
- 用户无法判断哪些头文件允许依赖。

### 15.2 目标 include 规则

建议将稳定接口逐步集中到：

```text
include/tflm/
```

例如：

```text
include/tflm/init/init_entry.hpp
include/tflm/irq/can_registry.hpp
include/tflm/drivers/stream.hpp
include/tflm/drivers/uart_dma.hpp
include/tflm/modules/imu.hpp
include/tflm/modules/remote.hpp
include/tflm/topic/remote_to.hpp
include/tflm/cmd/shell.hpp
```

具体设备协议细节仍可以留在模块私有目录：

```text
modules/imu/devices/icm42688p/
modules/remotes/dr16/
```

### 15.3 公共接口规则

可以被业务仓库 include 的头文件必须满足：

- 不依赖业务仓库路径；
- 不暴露不必要的私有成员；
- 不要求业务手工定义内部宏；
- 不要求业务复制实现文件；
- 对线程安全和调用上下文有说明；
- 对初始化前后状态有明确要求；
- 对失败返回值有明确含义；
- 对数据单位和时间戳有明确说明。

### 15.4 过渡阶段

不需要一次性移动所有头文件。

可以采用：

```text
旧路径继续可用
新路径作为推荐公共接口
文档和新业务只使用新路径
旧路径逐步标记 deprecated
```

这样可以避免一次性破坏当前工程和实验代码。

## 16. 注册宏的公共 ABI

### 16.1 为什么注册宏适合外部业务

注册宏的价值在于：

```text
新增一个实现
    -> 在本地文件写一个注册声明
    -> 编译器和链接器自动收集
    -> 框架统一遍历
```

业务项目可以因此做到：

- 新增 Remote 协议不改中央协议列表；
- 新增 IMU 数据源不改 ImuManager；
- 新增 Shell 参数不改 Shell；
- 新增 CAN ID 分发不改中央 switch；
- 新增初始化项不改 main；
- 新增实验模块不改框架核心。

### 16.2 注册段必须成为稳定契约

注册段不是普通实现细节。外部业务依赖它后，必须明确：

- section 名称；
- entry 结构体布局；
- start/end 符号；
- 对齐要求；
- `KEEP()` 要求；
- 编译器属性；
- LTO 下的保留规则；
- 空表行为；
- 重复注册行为；
- 版本兼容策略。

### 16.3 注册宏命名空间

当前宏名称较短：

```text
REGISTER_INIT
REGISTER_REMOTE
REGISTER_IMU
REGISTER_SHELL_VAR
CAN_RX_HANDLER
```

如果 tflm 独立开源，建议评估：

```text
TFLM_REGISTER_INIT
TFLM_REGISTER_REMOTE
TFLM_REGISTER_IMU
TFLM_REGISTER_SHELL_VAR
TFLM_CAN_RX_HANDLER
```

也可以保留短宏作为公共接口，把底层实现宏加前缀：

```cpp
#define REGISTER_INIT(...) TFLM_REGISTER_INIT(__VA_ARGS__)
```

最终选择要考虑：

- 可读性；
- 与 Zephyr 宏冲突；
- 用户使用频率；
- 头文件污染；
- 兼容周期。

### 16.4 注册宏与 Kconfig 的关系

注册宏本身不应该绕过 Kconfig。

正确关系是：

```text
Kconfig
    -> 决定某个源文件是否参与编译

CMake
    -> 把启用的源文件加入目标

注册宏
    -> 只对已经编译进来的实现进行链接收集
```

因此，未启用功能不会因为某个公共头文件被 include 就自动进入固件。

## 17. 框架版本与业务版本

### 17.1 版本职责

框架版本描述：

- 公共接口；
- Kconfig 符号；
- topic 契约；
- 注册段 ABI；
- drivers/modules/algorithm/cmd 能力；
- 支持的 Zephyr 范围；
- 已验证的板卡和工具链。

业务版本描述：

- 机器人业务；
- 板卡配置；
- 控制参数；
- 线程调度；
- 设备拓扑；
- 比赛策略；
- 实验数据。

两者不能混成一个版本号。

### 17.2 建议版本关系

```text
tflm v0.1.0
robot-sentry v0.1.0
Zephyr v4.x.y
board hpm5361icb-revA
```

业务仓库通过 `west.yml` 固定：

```yaml
manifest:
  projects:
    - name: tflm
      url: <tflm-repository>
      revision: v0.1.0
      path: modules/lib/tflm
```

实际远程地址和 revision 策略在开源前确定。

### 17.3 分支策略

建议至少区分：

```text
main
    -> 可被业务使用的稳定主线

develop
    -> 框架演进和接口实验

feature/*
    -> 新模块、重构、实验能力

release/*
    -> 发布前冻结和兼容检查
```

业务项目不应长期依赖 tflm 的任意工作区状态。

### 17.4 版本锁定规则

开发阶段可以：

```text
使用本地路径模块
```

比赛和发布阶段必须：

```text
使用 tag 或 commit 锁定模块
```

不要让比赛固件依赖：

```text
本地未提交修改
未锁定的 main 分支
机器上的绝对路径
某个开发者个人目录
```

## 18. 当前绝对路径和仓库耦合问题

当前工程中存在一些适合本地开发、但不适合外部使用的写法：

```cmake
set(SDK_GLUE_DIR "D:/Zephyr_HPMicro/sdk_glue")
set(ZEPHYR_SDK_INSTALL_DIR "D:/Zephyr/zephyr-sdk-0.16.8")
set(ZEPHYR_EXTRA_MODULES
    "D:/Zephyr_HPMicro/modules/lib/CherryUSB"
    "D:/Zephyr/modules/user/usb"
)
```

这些路径不能进入最终开源框架接口。

### 18.1 目标做法

板卡和 SDK glue 应该由业务工作区或 board integration 提供：

```text
业务 west.yml
    -> 获取 Zephyr、SDK glue、CherryUSB、USB module

业务 board.cmake
    -> 设置板卡所需的 runner 和路径

tflm
    -> 不知道用户电脑上 SDK 放在哪里
```

### 18.2 外部 USB 模块

当前 `drivers/usb` 的特殊性仍然需要保留：

```text
tflm project-side USB Stream adapter
    -> 提供 Stream 语义

外部 USB module
    -> 提供 USB device stack、CDC ACM、HPM HAL、IRQ/DMA
```

在目标架构中，业务仓库的 west manifest 应该同时声明：

```text
Zephyr
tflm
CherryUSB
HPM USB module
SDK glue
```

tflm 不应该把某个开发机上的 USB module 绝对路径写进根 CMake。

### 18.3 当前 `ZEPHYR_EXTRA_MODULES` 的迁移

当前根 CMake 中的额外模块路径属于本地集成方式，后续需要统一为：

```text
west manifest
    -> 负责版本和仓库来源

Zephyr module discovery
    -> 负责模块进入构建系统

业务 CMake 的额外模块变量
    -> 只作为本地开发覆盖
```

具体变量名称、优先级和 Zephyr 版本兼容性应在迁移时通过实际构建验证，不应继续把本地绝对路径作为公共接口。

## 19. 参考项目如何保留

框架仓库不能完全没有示例，否则新用户很难学习如何使用。

但示例应该被明确标记为：

```text
reference application
```

而不是：

```text
框架唯一真实项目
```

建议结构：

```text
examples/
├── minimal/
│   ├── CMakeLists.txt
│   ├── prj.conf
│   └── app/
├── imu_bringup/
│   ├── CMakeLists.txt
│   ├── boards/
│   └── app/
└── reference_robot/
    ├── CMakeLists.txt
    ├── Kconfig
    ├── boards/
    └── app/
```

当前 `project/` 可以先迁移为：

```text
examples/reference_robot/
```

或者：

```text
examples/current_project/
```

如果暂时不移动目录，也应该在文档中明确：

```text
当前 project/ 是内置参考业务，目标架构中的业务仓库可以完全替换它
```

### 19.1 示例必须证明什么

最少需要保留三个示例：

#### 最小框架示例

证明：

- tflm module 可以被发现；
- Kconfig 可以打开；
- 一个驱动可以被业务使用；
- 一个初始化项可以注册；
- 不需要复制整个项目。

#### 设备验证示例

证明：

- IMU 或 Remote 可以独立验证；
- Shell 可以独立调参；
- Python 脚本可以参与实验；
- 设备模块不依赖完整机器人业务。

#### 整机参考示例

证明：

- 多个模块可以组合；
- topic 可以传递数据；
- project/thread 可以承载底盘、云台等控制；
- CAN 中断注册和启动注册可以在业务侧完成。

## 20. 迁移策略

不建议直接删除当前 `project/` 或直接改成完全独立仓库。

建议分为六个阶段。

### 阶段 0：边界审计

目标：

```text
知道哪些文件是框架能力，哪些文件是当前业务
```

需要完成：

- 标记 drivers/modules/algorithm/topic/cmd 中的公共代码；
- 标记 project 中的业务代码；
- 标记 project 中可公共化的注册协议；
- 标记硬编码板卡和绝对路径；
- 标记当前只在参考业务中使用的 topic；
- 标记当前只有计划、尚未落地的 Remote 双 UART；
- 标记外部 USB module 的依赖位置；
- 建立公共头文件候选清单。

输出：

```text
框架目录清单
业务目录清单
公共接口清单
迁移风险清单
```

这一阶段不改行为，只做边界确认。

### 阶段 1：先把框架接口稳定下来

目标：

```text
新业务不需要 include project/apps 内部文件
```

优先抽取：

- `InitEntry` 和 `REGISTER_INIT`；
- `CanRxEntry` 和 `CAN_RX_HANDLER`；
- Shell 注册接口；
- Remote 注册接口；
- IMU 注册接口；
- Stream 公共接口；
- topic 公共头文件；
- 版本信息。

目标目录：

```text
include/tflm/
```

阶段 1 不要求拆仓库，先在当前仓库中完成公共接口。

### 阶段 2：增加 Zephyr module 外壳

目标：

```text
tflm 可以作为 module 被一个最小外部应用发现和编译
```

需要增加：

```text
zephyr/module.yml
zephyr/CMakeLists.txt
zephyr/Kconfig
```

需要验证：

- module.yml 能被 west 发现；
- Kconfig 能显示 tflm 菜单；
- tflm 驱动能进入 app；
- tflm 模块能进入 app；
- linker section 能被加入；
- 外部业务能 include 公共头文件；
- 没有依赖当前根 `project/`；
- 没有依赖本机绝对路径。

可以创建一个最小验证仓库：

```text
temp/tflm_consumer_smoke/
```

但这个验证仓库最好最终变成正式 example，而不是永久放在 `temp/`。

### 阶段 3：把当前 project 变成参考业务

目标：

```text
框架构建不再硬编码当前 project
```

迁移动作：

1. 把当前根应用 CMake 复制为 `examples/reference_robot/CMakeLists.txt`；
2. 把当前 `project/` 移到 `examples/reference_robot/app/`；
3. 把当前板级配置移到示例自己的 `boards/`；
4. 让 tflm module 只负责框架目录；
5. 让示例应用自己选择 tflm 能力；
6. 让根仓库继续提供一个兼容入口一段时间；
7. 文档全部改成“参考业务”而不是“框架默认业务”。

这个阶段完成后，框架核心的 CMake 不应该出现：

```text
ACTIVE_PRJ
PROJ_DIR
CONFIG_PRJ_TEST
project/thread
project/boards
```

除非这些内容位于 example 的 CMake 中。

### 阶段 4：使用独立业务仓库验证

目标：

```text
新建一个完全不包含 tflm 源码的业务仓库
```

这个仓库至少要完成：

- 通过 west 拉取 tflm；
- 通过 `prj.conf` 选择能力；
- 通过 board overlay 绑定硬件；
- 创建一个业务线程；
- 调用 IMU 或 Remote；
- 注册一个初始化项；
- 注册一个 Shell 变量；
- 使用一个公共 topic；
- 构建出固件。

最好不要直接把当前参考机器人复制过去，而是从最小功能开始：

```text
一个板卡
一个 UART
一个模块
一个线程
一个 Shell 变量
```

只有最小消费者成功，才能说明框架真的可以被外部使用。

### 阶段 5：版本化和兼容检查

目标：

```text
tflm 具备可被别人依赖的发布能力
```

需要建立：

- tag；
- CHANGELOG；
- 迁移说明；
- 公共接口清单；
- Kconfig 变更说明；
- topic 变更说明；
- Zephyr 版本支持范围；
- 已验证 board 列表；
- 已知限制；
- 示例应用；
- 最小消费者工程；
- 本地路径覆盖说明。

### 阶段 6：多业务项目验证

目标：

```text
同一版本 tflm 被两个不同业务仓库使用
```

两个项目应该尽量有不同特点：

```text
项目 A
    -> HPM 板卡 + IMU + Remote + 底盘

项目 B
    -> STM32 板卡 + 其他传感器 + Shell + 测试线程
```

如果两个项目都必须修改 tflm 的业务文件才能编译，说明边界仍然没有真正稳定。

## 21. 迁移过程中的兼容层

### 21.1 为什么需要兼容层

当前工程已经有大量代码依赖：

```text
project/apps/Init_entry.hpp
project/apps/Irq_handlers.h
drivers/communication/...
modules/...
```

如果一次性移动所有文件，容易导致：

- 当前比赛代码无法构建；
- 实验脚本失去验证对象；
- 文档和代码同时失配；
- 调试周期被架构迁移打断。

因此需要保留一段兼容期。

### 21.2 兼容层形式

可以用转发头文件：

```cpp
// project/apps/Init_entry.hpp
#pragma once
#include <tflm/init/init_entry.hpp>
```

可以用旧宏映射：

```cpp
#define MOD_DEV_IMU TFLM_MOD_DEV_IMU
```

可以用旧目录的 wrapper：

```text
modules/imu/imu.hpp
    -> include/tflm/modules/imu.hpp
```

兼容层的目标是：

```text
让旧业务暂时能运行
让新业务只使用新接口
```

兼容层不应该继续增加新功能。

### 21.3 兼容层的删除条件

满足以下条件后，才删除旧接口：

- 至少有一个外部业务仓库已经使用新接口；
- 参考业务已经完成迁移；

## 23. 公共接口的稳定性等级

外部业务使用后，不同接口应该有不同稳定等级。

### 稳定接口

这些接口一旦发布就应该谨慎修改：

- `Stream`；
- `UartDma`；
- IMU 公共数据结构；
- Remote 输出消息；
- Motor 快照；
- PowerMeter 快照；
- `REGISTER_INIT`；
- `REGISTER_REMOTE`；
- `REGISTER_IMU`；
- `REGISTER_SHELL_VAR`；
- 公共 topic。

### 半稳定接口

这些接口可以演进，但需要迁移说明：

- 线程模板；
- 初始化阶段；
- 具体算法类；
- Flash 分区；
- Buzzer 宏；
- USB Stream 适配器。

### 私有接口

这些接口不承诺外部业务直接使用：

- 具体设备私有寄存器函数；
- `modules/imu/devices/*` 内部辅助函数；
- Remote parser 内部缓冲区；
- Shell 内部命令解析器；
- linker script 内部辅助符号；
- 当前实现中的临时状态字段。

公共文档必须明确接口等级，避免用户直接依赖内部实现。

## 24. 新增功能时的决策流程

以后新增一个功能，可以按照下面的顺序判断。

### 问题一：这个功能是否与具体机器人无关

如果无关，优先考虑放入：

```text
drivers/
modules/
algorithm/
topic/
cmd/
```

如果高度依赖当前机器人状态机，放入业务仓库。

### 问题二：它是硬件访问、设备能力还是业务策略

```text
直接访问 Zephyr device
    -> drivers

封装一个可使用的设备
    -> modules

纯计算和状态更新
    -> algorithm

跨线程数据契约
    -> topic

调试、提示、Flash 等横切辅助
    -> cmd

多设备协同和机器人决策
    -> business app/thread
```

### 问题三：它是否需要独立线程

```text
主动连续产生数据
    -> 模块可以拥有线程

硬件回调即可更新快照
    -> 模块不拥有线程

需要多个设备协同决策
    -> 业务线程拥有线程
```

这与当前 IMU、Remote、Motor、PowerMeter 的线程归属保持一致。

### 问题四：它是否应该进入公共 topic

```text
多个业务都需要，语义稳定
    -> tflm topic

只有当前机器人需要
    -> business topic

只用于实验
    -> test topic 或脚本协议
```

### 问题五：是否需要注册宏

如果新增功能需要：

- 被框架自动发现；
- 避免中央列表；
- 支持按编译单元裁剪；
- 允许多个实现共存；
- 支持业务侧扩展；

可以考虑注册宏。

如果只有一个固定实现，普通函数或对象可能更清晰。

    -> 双 UART 冗余

    -> remote_to

    -> 映射为底盘、云台和发射控制

    -> Can

## 31. 最终判断

这套规划不是要把业务层从架构中“赶出去”，而是要把业务层放到更正确的位置：

```text
业务层不再是框架仓库里的一部分实现
业务层变成使用框架能力的外部应用
```

同时，业务层仍然会被编译到同一个固件中，仍然可以：

- 使用框架初始化机制；
- 使用框架中断注册机制；
- 使用框架驱动；
- 使用框架模块；
- 使用框架算法；
- 使用框架 topic；
- 使用框架 Shell；
- 使用框架 linker section；
- 使用框架 Python 实验工具。

真正改变的是依赖方向和维护方式。

最终理想状态是：

```text
tflm 负责回答：
    如何提供可复用的嵌入式能力

业务项目负责回答：
    当前机器人如何使用这些能力
```

再用一句话概括：

> tflm 不应该成为一台机器人的完整工程副本，而应该成为许多机器人项目可以共同依赖的一棵架构树；每个业务仓库只需要把自己的应用、板卡、线程和实验嵌入这棵树中。

这条路线也最符合当前架构已经形成的方向：

```text
drivers
    -> 访问硬件

modules
    -> 封装设备能力

algorithm
    -> 提供纯计算

topic
    -> 提供数据契约

cmd
    -> 提供运行时辅助

project/app
    -> 组合成具体业务

scripts
    -> 完成主机侧验证闭环
```

下一步不需要立刻重写所有代码。最值得优先做的是：

1. 抽取公共初始化和中断注册接口；
2. 增加最小 `zephyr/module.yml`；
3. 用一个完全不依赖当前 `project/` 的最小业务消费者验证；
4. 再把当前 `project/` 迁移成参考业务。

只要最小消费者能真正使用 tflm，架构就从“一个组织良好的单仓库工程”迈入了“可以被业务工程依赖的框架”。
