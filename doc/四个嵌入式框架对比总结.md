## 一、阅读范围与比较方法

### 1.1 比较对象

本文比较以下四个项目：

1. `temp/basic_framework-master`
2. `temp/COD_H7_Template_CLion-main`
3. `temp/Dust_SentinelRobot_L_Game`
4. 当前仓库 `tflm`

用户之前称呼的 `temp/COD-H7`，在当前工作区中的实际目录名是：

```text
temp/COD_H7_Template_CLion-main
```

后文统一使用 `COD_H7` 作为简称。

### 1.2 为什么不能只按“文件多少”判断框架好坏

四个项目处于不同的开发目标中。

有的项目首先解决队伍传承问题。

有的项目首先解决一块控制板能否快速开始开发的问题。

有的项目首先解决一台具体机器人能否形成完整业务闭环的问题。

有的项目首先解决多个项目之间如何共享框架能力的问题。

如果把这四个项目直接排成一个“高级到低级”的顺序，结论一定会失真。

例如：

- 一个项目可能平台化能力很强，但当前还没有完整比赛机器人；
- 一个项目可能没有通用框架边界，但整机控制链已经非常成熟；
- 一个项目可能文档很多，但编译系统和项目隔离仍然依赖人工维护；
- 一个项目可能目录简单，但对于固定单板的快速联调反而最高效。

因此本文不使用单一排名作为主要结论。

本文先看每个项目到底在解决什么问题。

然后看它的真实代码路径：

```text
入口
  -> 初始化
  -> 任务创建
  -> 数据采集
  -> 控制计算
  -> 输出发送
```

最后再按照不同目标分别评价：

- 框架架构能力；
- 单板开发效率；
- 单台机器人整机能力；
- 跨项目迁移能力；
- 维护和传承能力。

### 1.3 本文使用的五个核心评价维度

为了避免每个项目使用一套不同的标准，本文统一使用以下五个维度。

#### 维度一：运行时基础

关注项目依赖什么运行时和系统能力：

- 裸机、HAL、FreeRTOS 还是 Zephyr；
- 是否有明确的线程模型；
- 是否有统一的初始化和失败处理方式；
- 是否能够表达线程、模块和板级能力之间的依赖。

#### 维度二：职责边界

关注以下问题：

- 驱动是否只负责硬件；
- 算法是否与线程和设备解耦；
- 设备模块是否拥有明确接口；
- 业务线程是否直接进入底层硬件；
- 项目差异是否有固定归属。

#### 维度三：装配和迁移能力

关注换一块板、换一台机器人、换一套设备拓扑时，需要修改什么：

- 只改配置；
- 只改项目层；
- 复制整套工程；
- 还是需要穿透多个目录手工调整。

#### 维度四：维护和传承能力

关注后来者是否可以通过边界和文档理解系统，而不必依赖原作者记忆。

这里的“传承”不等于文档数量。

真正重要的是：

- 入口是否稳定；
- 依赖方向是否明确；
- 数据所有权是否明确；
- 初始化责任是否明确；
- 新功能应该放在哪里是否容易判断。

#### 维度五：真实业务闭环

关注项目能否直接承载真实机器人：

- 设备通信；
- 传感器采样；
- 状态估计；
- 控制计算；
- 电机输出；
- 失联处理；
- 模式切换；
- 整机策略。

这个维度和“框架架构能力”不是一回事。

一台真实机器人可能业务闭环很强，但平台化能力并不高。

## 二、先给结论

### 2.1 四个项目的一句话定位

| 项目 | 最准确的定位 |
| --- | --- |
| `basic_framework-master` | 以 `bsp / module / app`、实例和消息契约为中心的队伍级 STM32 基础框架 |
| `COD_H7` | 以 STM32H723、CubeMX、FreeRTOS、固定任务和 C 组件为中心的单板电控模板 |
| `Dust_SentinelRobot_L_Game` | 以 `Robot` 对象、设备拓扑和总控任务为中心的具体机器人整机工程 |
| `tflm` | 以 `project/` 装配、Kconfig/CMake 裁剪和注册式初始化为中心的 Zephyr 平台骨架 |

### 2.2 四种不同的系统组织中心

这四个项目最根本的差异，不是 C 和 C++ 的差异。

也不是目录名字是否相似。

而是它们选择了不同的“系统组织中心”：

```text
basic_framework-master
    -> 层级、实例和消息契约

COD_H7
    -> 板级底座、固定任务和 C 组件

Dust_SentinelRobot_L_Game
    -> 整机对象、设备拓扑和总控任务

tflm
    -> 项目装配、编译裁剪和初始化注册
```

它们分别优先回答了四个问题：

```text
如何让队伍长期复用？
如何从一块高性能控制板快速开始？
如何把一台机器人完整做出来？
如何把项目差异收敛到项目层？
```

### 2.3 如果只看框架架构能力

在当前代码快照下，我会给出：

```text
tflm
    >
basic_framework-master
    >
COD_H7
    >
Dust_SentinelRobot_L_Game
```

这里的排序依据是：

- 项目边界是否明确；
- 编译期是否可以裁剪；
- 初始化是否可以注册；
- 模块是否能够脱离具体项目；
- 新项目是否能主要修改项目层。

这个排序不是在说 Dust 代码质量差。

它只是在说 Dust 的第一目标不是做平台。

### 2.4 如果只看单台比赛整机能力

排序应该反过来关注业务闭环：

```text
Dust_SentinelRobot_L_Game
    >
basic_framework-master
    >
tflm
    >
COD_H7
```

原因是：

- Dust 已经围绕一台机器人把通信、控制、保护和总控策略连成闭环；
- `basic_framework-master` 具备成熟的机器人应用和模块底座；
- `tflm` 的框架上限最高，但当前项目仍处于持续装配和收敛阶段；
- COD_H7 当前快照更接近一套完整单板模板和控制骨架，尚未体现同等规模的整机业务。

### 2.5 最短总结

可以把四个项目概括成四句话：

- `basic_framework-master` 把经验整理成了队伍规则。
- `COD_H7` 把一块 H7 控制板整理成了可复用模板。
- `Dust_SentinelRobot_L_Game` 把设备和策略组织成了一台能工作的机器人。
- `tflm` 开始把项目差异从框架层中剥离出来。

## 三、四个项目的整体画像

### 3.1 组织方式总表

| 对比项 | `basic_framework-master` | `COD_H7` | `Dust` | `tflm` |
| --- | --- | --- | --- | --- |
| 主要语言 | C | C | C/C++ 以 C++ 为主 | C/C++ |
| 主要运行时 | STM32 HAL + FreeRTOS | STM32 HAL + FreeRTOS | STM32 HAL + FreeRTOS | Zephyr |
| 工具链中心 | CubeMX/工程配置 | CubeMX + CMake + CLion/Ninja | CubeMX/工程配置 | CMake + Kconfig + Zephyr |
| 组织中心 | 层级、实例、消息 | 单板、任务、组件 | Robot、成员对象、总控 | project、注册项、配置 |
| 任务创建 | 集中任务初始化 | `freertos.c` 集中创建 | 对象初始化时分散创建 | 线程本地注册初始化项 |
| 线程通信 | message center | 全局结构体和直接调用 | 成员对象直接读写 | zbus、k_msgq、接口调用 |
| 硬件绑定 | BSP 和实例配置 | CubeMX 和 BSP 宏 | 设备对象及具体 ID | DTS、驱动类和项目板级配置 |
| 项目裁剪 | 宏和工程约定 | 固定源目录和手工删改 | 复制工程后改造 | Kconfig/CMake |
| 当前强项 | 传承和规则 | 单板快速启动 | 整机落地 | 跨项目平台化 |
| 当前代价 | 规则有人工约束 | 全局状态和固定拓扑 | 总控偏重 | 抽象较多、还在收敛 |

### 3.2 四个项目不在同一抽象层级

`basic_framework-master` 更接近“队伍 SDK”。

它试图将多个机器人项目共同需要的规则和基础模块固化下来。

`COD_H7` 更接近“控制板模板”。

它把一块 STM32H723 单板上常见的外设、组件和任务预先准备好。

`Dust` 更接近“产品工程”。

它把某台机器人的设备拓扑和控制策略直接组织到一起。

`tflm` 更接近“平台内的项目单元”。

它把框架能力和具体项目装配拆开，并把构建、板级配置和线程开关串起来。

因此，比较时必须先问：

```text
你是在比较平台，还是在比较产品？
```

如果把产品直接拿去和平台比较，平台一定显得业务不够完整。

如果把平台直接拿去和产品比较，产品一定显得复用边界不够清晰。

### 3.3 复杂度分别集中在哪里

四个项目并不是“复杂度不同”，而是复杂度放置位置不同。

#### `basic_framework-master`

复杂度主要放在：

- 分层规则；
- 实例注册；
- 消息中心；
- 多板切换；
- 任务频率约定；
- 文档体系。

#### `COD_H7`

复杂度主要放在：

- CubeMX 外设初始化；
- BSP 回调；
- 全局设备数组；
- 固定任务；
- 具体 CAN/UART 拓扑；
- 组件之间的头文件依赖。

#### Dust

复杂度主要放在：

- `Robot` 成员对象；
- 设备 ID 和回调分发；
- 跨模块策略；
- 每个对象的独立任务；
- 整机模式和故障处理。

#### `tflm`

复杂度主要放在：

- Kconfig；
- CMake；
- DTS 和板级目录；
- 初始化注册；
- topic 通道；
- 框架层与项目层之间的调用链。

这也是为什么初次阅读 `tflm` 可能比 COD_H7 更慢。

它把原来隐藏在一个工程文件和几个全局对象里的关系显式拆开了。

## 四、basic_framework-master：队伍级基础框架

### 4.1 定位

`basic_framework-master` 是四个项目中最明显以“队伍长期复用”为目标的项目。

它不是只为某一台机器人写控制逻辑。

它希望把多个赛季、多个兵种和多个成员共同需要的底层能力沉淀下来。

它的主要组织语言是：

```text
bsp
    ↓
module
    ↓
application
```

在应用之间，又通过消息中心建立数据交换关系。

因此它同时使用两种组织方式：

1. 用层级表达依赖方向；
2. 用消息契约减少并列应用之间的直接包含。

### 4.2 代码组织

它的核心思想可以简化为：

```text
BSP
    负责板级硬件

Module
    负责可复用设备和算法能力

Application
    负责具体机器人行为
```

例如：

- 电机实例属于模块能力；
- 底盘应用组合多个电机实例；
- 云台应用组合云台电机和姿态数据；
- 机器人指令应用解析遥控器或上位机输入；
- 应用之间通过 `message_center` 交换命令和反馈。

这种组织方式特别适合多人协作。

一个成员可以维护底盘模块。

另一个成员可以维护云台应用。

只要消息结构和应用边界稳定，双方不需要把所有对象直接包含进来。

### 4.3 初始化和任务模型

从 `application/robot.c`、`application/robot_task.h` 等入口看，它的初始化思路比较集中。

典型链路可以概括为：

```text
main
  -> RobotInit()
      -> BSPInit()
      -> RobotCMDInit()
      -> GimbalInit()
      -> ShootInit()
      -> ChassisInit()
      -> OSTaskInit()
  -> 启动 FreeRTOS
```

这种方式的优点是阅读路径很短。

新人先找到机器人初始化函数。

再找到任务创建函数。

然后沿着应用层入口向下阅读。

它没有把初始化责任散落到几十个类中。

### 4.4 应用通信模型

`message_center` 是它最有代表性的设计之一。

控制命令和反馈数据不一定通过应用对象直接传递。

更典型的关系是：

```text
robot_cmd
    -> 发布 chassis_cmd
    -> 发布 gimbal_cmd
    -> 发布 shoot_cmd

chassis
    -> 发布 chassis_feed

gimbal
    -> 发布 gimbal_feed

shoot
    -> 发布 shoot_feed
```

也可以画成：

```text
robot_cmd
    -> message_center
        -> chassis
        -> gimbal
        -> shoot

chassis
gimbal
shoot
    -> message_center
        -> robot_cmd
```

这种模式解决了一个常见问题：

```text
底盘不需要直接包含云台；
云台不需要直接包含发射；
robot_cmd 不需要持有每个应用的具体对象。
```

应用之间依赖的是消息结构，而不是对象布局。

### 4.5 它的优势

#### 规则和文档完整

它不仅有代码目录。

还有架构介绍、开发指南、APP 编写指引、消息中心说明和模块文档。

这使它更像一个可以交接的工程平台。

#### 多机器人复用意识强

通过 `robot_def.h` 和相关配置，它可以在单板、双板、不同机器人角色之间进行切换。

这种方式不一定是最现代的配置系统。

但对 STM32 工程来说已经形成了明确的平台意识。

#### 应用边界比较清楚

底盘、云台、发射和机器人指令各自有相对明确的责任。

跨应用的协调优先通过消息完成。

这比所有应用都直接调用对方函数更容易长期维护。

#### 接近真实队伍使用方式

它考虑的不只是代码能否编译。

还考虑：

- 新人能否找到入口；
- 不同成员能否并行开发；
- 多台机器人能否共用底座；
- 新赛季能否继续沉淀。

### 4.6 它的局限

#### 仍然深度绑定 STM32 生态

它的底层基础仍然是：

- STM32；
- HAL；
- CubeMX；
- FreeRTOS；
- 大量 C 风格配置和宏。

所以它的移植能力主要体现在同类 STM32 项目内部。

它不是面向不同 RTOS 和不同芯片族的通用平台。

#### 规则仍有人工维护成分

虽然它有分层和文档，但很多规则仍然依赖：

- 命名；
- 目录；
- 宏；
- 注册顺序；
- 开发纪律。

编译器并不会完整阻止错误依赖。

例如，某个应用如果直接包含另一个应用的头文件，项目结构本身未必会立刻报错。

#### 消息中心机制相对轻量

它的 pub-sub 机制足够支撑机器人项目。

但如果系统进一步增大，就需要持续关注：

- 队列容量；
- 数据覆盖；
- 并发保护；
- 消息生命周期；
- 发布者和订阅者的注册顺序。

### 4.7 适合什么场景

它适合：

- 队伍级基础平台；
- 多机器人共底座；
- 多成员并行协作；
- STM32/HAL/FreeRTOS 技术栈；
- 需要新人接手和长期传承的项目。

它不一定适合：

- 快速验证一块新板；
- 跨 RTOS 的平台抽象；
- 需要大量编译期模块裁剪的工程；
- 只为一台机器人写一次性业务。

### 4.8 一句话评价

> `basic_framework-master` 最强的地方不是某一个算法，而是它把队伍开发经验整理成了分层、消息、配置和文档规则。

## 五、COD_H7_Template_CLion-main：单板电控模板

### 5.1 定位

`COD_H7` 是一套面向 STM32H723 的高性能单板电控模板。

它的主要目标不是建立一个跨芯片平台。

也不是直接表达一台完整机器人的所有整机策略。

它更像是：

> 先把一块 STM32H7 控制板的外设、设备、算法和任务骨架整理好，让新项目可以直接从这块板开始开发。

它使用的技术组合是：

```text
STM32H723
    + STM32CubeMX
    + HAL
    + FreeRTOS
    + CMSIS-RTOS API
    + CMake
    + Ninja
    + CLion
```

### 5.2 实际目录结构

当前工程主要分成：

```text
Core/
    CubeMX 生成的 MCU、时钟、中断和外设初始化

Drivers/
    STM32H7 HAL、CMSIS

Middlewares/
    FreeRTOS、USB Device、ARM DSP

USB_DEVICE/
    USB CDC 应用

USER/
├── BSP/
│   ├── Inc/
│   └── Src/
├── Components/
│   ├── Device/
│   ├── Controller/
│   └── Algorithm/
└── Application/
    └── Task/
        ├── Inc/
        └── Src/
```

其中：

- `USER/BSP` 负责板级接口和外设辅助；
- `USER/Components/Device` 放 BMI088、电机、遥控器、裁判系统和图传等设备组件；
- `USER/Components/Controller` 放 PID；
- `USER/Components/Algorithm` 放 LPF、Kalman、Quaternion、RLS、Ramp、CRC；
- `USER/Application/Task` 放 INS、Control、CAN、Detect 四个任务。

这已经明显超过“所有用户代码都放在 `Core/Src`”的 CubeMX 默认工程。

但是需要区分：

```text
目录分区
    不等于
编译依赖已经严格隔离
```

COD_H7 的目录是清楚的。

但它的运行时和数据依赖仍然比较集中。

### 5.3 真实启动链

COD_H7 的启动链来自 `Core/Src/main.c`。

完整顺序可以概括为：

```text
main()
  -> MPU_Config()
  -> 开启 I-Cache / D-Cache
  -> HAL_Init()
  -> SystemClock_Config()
  -> PeriphCommonClock_Config()
  -> MX_GPIO_Init()
  -> MX_DMA_Init()
  -> MX_SPI2_Init()
  -> MX_ADC1_Init()
  -> MX_TIM3_Init()
  -> MX_FDCAN1_Init()
  -> MX_FDCAN2_Init()
  -> MX_FDCAN3_Init()
  -> MX_UART5_Init()
  -> MX_UART7_Init()
  -> MX_USART1_UART_Init()
  -> MCU_Init()
  -> MX_FREERTOS_Init()
  -> osKernelStart()
```

这里有两个不同层次的初始化。

第一层是 CubeMX 生成的 HAL 和外设句柄初始化。

第二层是 `MCU_Init()` 中的用户 BSP 和设备初始化。

`MCU_Init()` 当前执行：

```text
BSP_PWM_Init()
BSP_GPIO_Init()
BSP_FDCAN_Init()
BSP_USART_Init()
BSP_ADC_Init()
MX_USB_DEVICE_Init()
BMI088_Init()
```

这说明 `MCU_Init()` 不是纯粹的板级初始化函数。

它已经同时负责：

- 板级能力；
- USB 初始化；
- BMI088 设备初始化。

这也是 COD_H7 的一个重要边界特征：

```text
BSP 和具体设备初始化在同一条初始化链上。
```

### 5.4 任务创建模型

`Core/Src/freertos.c` 集中创建四个静态任务：

| 任务 | 优先级 | 栈空间 | 主要职责 |
| --- | --- | ---: | --- |
| `INS_Task` | `osPriorityHigh` | 1024 | BMI088、滤波、姿态解算、加热 |
| `Control_Task` | `osPriorityAboveNormal` | 1024 | 控制测量、目标、PID 和调试输出 |
| `CAN_Task` | `osPriorityNormal` | 1024 | 电机使能、CAN 周期发送 |
| `Detect_Task` | `osPriorityBelowNormal` | 1024 | 遥控器状态监测 |

任务控制块和栈是静态定义的：

```text
osThreadId
uint32_t taskBuffer[1024]
osStaticThreadDef_t taskControlBlock
```

任务创建点集中在：

```text
MX_FREERTOS_Init()
```

这种模型非常直观。

阅读者可以在一个文件里看到：

- 所有任务；
- 任务优先级；
- 栈大小；
- 任务入口；
- 任务创建顺序。

但它的代价也很直接：

- 任务集合是固定的；
- 新增任务需要修改集中式文件；
- 任务是否参与编译没有 Kconfig 开关；
- 任务依赖没有独立的配置表达；
- 任务和模块之间的边界主要由头文件和全局对象维持。

### 5.5 CAN 数据路径

COD_H7 的 CAN 路径非常短。

以 FDCAN1 为例：

```text
FDCAN 中断
  -> HAL_FDCAN_RxFifo0Callback()
  -> FDCAN1_RxFifo0RxHandler()
  -> DJI_Motor_Info_Update()
  -> Chassis_Motor[0..3]
```

FDCAN2 的路径是：

```text
FDCAN 中断
  -> HAL_FDCAN_RxFifo1Callback()
  -> FDCAN2_RxFifo1RxHandler()
  -> DM_Motor_Info_Update()
  -> DM_8009_Motor[0..3]
```

`bsp_can.c` 直接包含：

```c
#include "Motor.h"
#include "Remote_Control.h"
```

并且直接调用具体电机更新函数。

因此它不是：

```text
底层 CAN 驱动
    -> 通用事件
        -> 上层设备模块
```

而是：

```text
HAL CAN 回调
    -> BSP 回调处理
        -> 具体电机全局数组
```

这种路径的优点是调试非常快。

收到一帧 CAN 后，沿着代码很快就能找到数据最终写入的位置。

缺点是：

- BSP 知道具体设备类型；
- BSP 知道具体电机数组；
- 更换电机协议时需要进入 BSP 修改；
- 新增一类 CAN 设备时，容易继续向回调中堆逻辑。

### 5.6 UART 数据路径

`bsp_uart.c` 使用 DMA 双缓冲和空闲线接收。

当前 UART 数据关系大致是：

```text
UART5
    -> SBUS DMA 双缓冲
    -> USER_USART5_RxHandler()
    -> SBUS_TO_RC()
    -> remote_ctrl
```

USART1 通过宏 `USART1_RX_Switch` 在两种用途之间切换：

```text
USART1
    -> 图传数据
    -> Image_Transmission_Info_Update()
```

或者：

```text
USART1
    -> 裁判系统数据
    -> Referee_System_Frame_Update()
```

这种设计很适合固定板卡上的快速调试。

修改一个宏，就可以切换 USART1 的接收对象。

但它也说明：

```text
外设实例、协议用途和业务设备之间绑定较紧。
```

如果新项目同时需要图传和裁判系统，就不能只通过一个简单的功能开关解决。

### 5.7 INS 任务的数据链

`INS_Task.c` 把多个能力集中到一个任务里：

```text
BMI088_Info_Update()
    -> 加速度二阶低通
    -> 陀螺仪数据转换
    -> QuaternionEKF_Update()
    -> 欧拉角和角速度更新
    -> BMI088_Temp_Control()
    -> Heat_Power_Control()
```

当前任务周期是 1 ms。

姿态解算调用使用固定的：

```c
QuaternionEKF_Update(..., 0.001f);
```

这说明它以固定周期控制为主。

它的优点是：

- 采样；
- 滤波；
- 姿态；
- 温控；

全部在一个明确任务中完成。

它的缺点是：

- 任务既承担设备读取，又承担算法组合；
- 传感器设备、算法状态和 PWM 输出在同一个任务源文件里；
- 其他任务读取姿态时主要依赖全局 `INS_Info`；
- 更换 IMU 或姿态算法时，需要同时检查任务代码和全局数据结构。

### 5.8 Control 和 CAN 任务的关系

`Control_Task.c` 直接包含：

```c
#include "Remote_Control.h"
#include "PID.h"
#include "Motor.h"
```

它直接读取：

```c
remote_ctrl.rc.ch[3]
Chassis_Motor[0].Data.Velocity
```

然后写入：

```c
Control_Info.SendValue[]
```

`CAN_Task.c` 再直接包含：

```c
#include "Control_Task.h"
#include "INS_Task.h"
#include "Motor.h"
#include "bsp_can.h"
#include "Remote_Control.h"
```

它读取 `Control_Info.SendValue[]` 并组装 FDCAN 发送帧。

数据链可以画成：

```text
remote_ctrl
        \
         -> Control_Task
Chassis_Motor
         /

Control_Info.SendValue
        -> CAN_Task
        -> FDCAN1_TxFrame
        -> USER_FDCAN_AddMessageToTxFifoQ()
```

这里没有独立消息通道。

也没有显式的数据所有权协议。

数据路径短是它的效率来源。

全局状态和直接包含则是它的维护成本来源。

### 5.9 COD_H7 的优势

#### 单板硬件覆盖完整

当前工程已经覆盖：

- GPIO；
- DMA；
- SPI；
- ADC；
- TIM；
- 三路 FDCAN；
- 多路 UART；
- USB CDC；
- PWM；
- BMI088。

它很适合先把一块高性能控制板跑起来。

#### 任务骨架清楚

INS、Control、CAN、Detect 的任务分工直观。

优先级也在 `freertos.c` 中集中可见。

#### CMake 工具链比传统 IDE 工程更适合持续维护

根 `CMakeLists.txt` 明确使用：

- `gcc-arm-none-eabi`；
- `CMake`；
- `Ninja`；
- `compile_commands.json`；
- `arm_cortexM7lfdp_math`。

这对 CLion、clangd 和命令行构建比较友好。

#### 组件目录已经有复用意识

设备、控制器和算法不是全部堆在任务目录中。

`BMI088`、电机协议、PID、滤波器、四元数和 RLS 已经被单独整理。

#### 硬件数据链路短

对单板联调来说，短链路有很高价值。

收到 CAN 数据后，直接找到电机状态。

收到遥控器数据后，直接更新全局遥控器状态。

### 5.10 COD_H7 的局限

#### 任务装配是固定的

`MX_FREERTOS_Init()` 直接创建四个固定任务。

没有：

- Kconfig 功能开关；
- 线程自动注册；
- 按项目选择任务；
- 统一初始化等级；
- 初始化失败策略。

新项目如果不需要某个任务，通常需要手工修改工程文件或源码。

#### BSP 和设备模块存在穿透

`bsp_mcu.c` 同时负责 BSP 初始化、USB 初始化和 BMI088 初始化。

`bsp_can.c` 直接知道 Motor 模块和具体数组。

`bsp_uart.c` 直接知道遥控器、裁判系统和图传模块。

因此 `BSP` 在实际代码中不是严格的底层硬件边界。

#### 数据主要通过全局对象流动

典型全局对象包括：

- `remote_ctrl`；
- `Chassis_Motor[]`；
- `DM_8009_Motor[]`；
- `INS_Info`；
- `Control_Info`；
- `FDCAN1_TxFrame`；
- `FDCAN2_TxFrame`。

全局对象适合小规模工程。

当机器人数量、任务数量和数据来源继续增加时，数据写入方和读取方会越来越难追踪。

#### 构建系统还不是配置驱动框架

根 CMake 使用 `GLOB_RECURSE` 收集用户源文件。

它能减少手工列文件的工作量。

但它不能表达：

- 某个功能的模块依赖；
- 某个任务是否开启；
- 某个设备是否由项目选择；
- 某个板卡配置和项目配置的关系。

所以它是：

```text
CMake 化的单板工程
```

而不是：

```text
配置驱动的平台框架
```

#### 文档更偏仓库说明

当前 README 主要是项目名称和图片。

架构知识主要存在于：

- 目录；
- 注释；
- 函数名；
- 头文件依赖；
- 具体设备拓扑。

后来者仍然需要通过读代码理解：

- 谁初始化 BMI088；
- 谁更新电机状态；
- 谁拥有遥控器数据；
- 谁负责 CAN 发送；
- 哪些任务必须同时存在。

### 5.11 COD_H7 最适合的使用方式

它最适合：

1. 先拿一块 H7 控制板验证外设；
2. 复用现有 DMA、FDCAN、UART、SPI 和 USB 能力；
3. 快速加入 BMI088、电机和遥控器；
4. 用四个固定任务先跑通闭环；
5. 在业务稳定后再逐步抽离消息和配置边界。

它不应该被误判为：

```text
已经完成项目级平台化的框架
```

更准确的说法是：

> 它把“从一块 H7 单板开始开发机器人”的路径整理得很顺手，但还没有把“不同项目之间的装配差异”提升为一等概念。

## 六、Dust_SentinelRobot_L_Game：整机实战工程

### 6.1 定位

`Dust_SentinelRobot_L_Game` 是四个项目中最明显围绕一台具体机器人构建的项目。

它的第一目标不是打造一个长期通用 SDK。

它的第一目标是把哨兵机器人的整条链路打通：

- 上下板通信；
- 底盘；
- 云台；
- 拨弹；
- IMU；
- 超级电容；
- 裁判系统；
- 视觉或自瞄输入；
- 整机模式。

它更像：

```text
一个完整的产品工程
```

而不是：

```text
一个等待被多个项目复用的平台
```

### 6.2 Robot 是系统组织中心

Dust 的核心结构集中在：

```text
Interaction/Robot.h
Interaction/Robot.cpp
Interaction/Init.cpp
```

`Robot` 对象把主要功能对象组织在一起：

```text
Robot
├── McuComm
├── Chassis
├── Gimbal
├── Reload
├── Imu
├── Supercap
└── Referee
```

这种组织方式表达了一个非常直接的事实：

```text
这台机器人由哪些设备和功能组成？
```

相比只看目录，这种对象拓扑更接近整机工程师的思维。

### 6.3 启动和任务模型

Dust 的入口来自 CubeMX 生成的 FreeRTOS 工程。

典型启动链是：

```text
main()
  -> HAL 初始化
  -> MX_* 外设初始化
  -> osKernelInitialize()
  -> MX_FREERTOS_Init()
  -> StartDefaultTask()
      -> Init()
          -> can_init()
          -> uart_init()
          -> robot_.Init()
              -> mcu_comm_.Init()
              -> gimbal_.Init()
              -> chassis_.Init()
              -> reload_.Init()
              -> supercap_.Init()
              -> 其他对象初始化
          -> 创建或启动对象任务
  -> osKernelStart()
```

它和 COD_H7 的差异在于：

- COD_H7 主要在 `freertos.c` 集中创建四个任务；
- Dust 许多对象在自己的 `Init()` 内部创建自己的任务。

因此 Dust 的任务创建点更分散。

例如：

```text
Chassis::Init()
    -> 创建 chassis_task

Gimbal::Init()
    -> 创建 gimbal_task

Reload::Init()
    -> 创建 reload_task

Imu::Init()
    -> 创建 ImuTask
```

这种方式非常符合 C++ 对象模型。

对象不仅拥有状态和接口。

对象还拥有自己的运行任务。

### 6.4 CAN 接收模型

Dust 的 CAN 接收入口在 `Interaction/Init.cpp` 和通信相关文件中。

它会根据 CAN ID 直接分发到具体对象。

典型关系是：

```text
CAN1
  0x201 -> chassis motor 1
  0x202 -> chassis motor 2
  0x203 -> chassis motor 3
  0x204 -> chassis motor 4
  0x205 -> reload motor

CAN2
  0x01  -> mcu_comm
  0x07  -> gimbal yaw
  0x30  -> supercap
```

这条路径的优点是：

- ID 和设备关系直观；
- 回调到设备对象的链路短；
- 电机对象可以直接更新自己的状态；
- 调试具体设备时不需要穿过复杂消息系统。

它的代价是：

- CAN 分发入口知道很多业务设备；
- CAN ID 和设备拓扑写在具体工程中；
- 更换机器人时需要重新检查对象、ID 和回调关系；
- 业务设备和通信入口之间耦合较强。

### 6.5 Robot::Task 的作用

Dust 的 `Robot::Task()` 承担跨模块决策。

它可以直接读取：

- 上下板通信状态；
- 遥控器状态；
- 裁判系统状态；
- 自瞄或视觉状态；
- 底盘反馈；
- 云台反馈；
- 拨弹状态。

然后直接调用：

- `gimbal_`；
- `chassis_`；
- `reload_`；
- `supercap_`。

典型控制关系可以概括为：

```text
遥控器 / 视觉 / 裁判系统 / 上下板通信
                    ↓
              Robot::Task()
             ↙      ↓       ↘
        Gimbal   Chassis   Reload
```

这使复杂业务很容易落地。

例如：

- 裁判系统状态影响底盘模式；
- 上下板通信状态影响云台角度来源；
- 开火状态影响拨弹盘；
- 视觉状态影响自动瞄准；
- 机器人模式影响多个执行机构。

如果使用完全解耦的消息系统，这些关系需要先设计消息和反馈。

Dust 则直接在总控里表达。

因此它的短期开发效率很高。

### 6.6 Dust 的优势

#### 业务闭环最完整

它不是只提供底层驱动。

而是把：

- 通信；
- 控制；
- 模式；
- 故障；
- 整机策略；

放到了一个真实机器人系统中。

#### 对象拓扑清楚

通过 `Robot` 的成员对象，阅读者可以快速知道整机由什么组成。

这比在多个全局文件中搜索设备实例更直接。

#### 复杂策略实现效率高

跨模块策略直接写在总控中。

无需先引入新的消息类型和订阅关系。

#### 具有较强的工程实战感

包括：

- CAN 回调分发；
- 电机失联；
- 临界区复制共享数据；
- 运行模式；
- 功率和超级电容；
- 上下板状态；

这些都是实际机器人会遇到的问题。

### 6.7 Dust 的局限

#### Robot 容易变重

随着功能增加，`Robot` 和 `Robot::Task()` 会吸收越来越多策略。

当继续加入：

- 自动导航；
- 更多视觉模式；
- 能量机关；
- 复杂故障状态机；
- 多套行为模式；

总控就可能成为一个大型协调中心。

#### 目录分区不等于依赖规则

Dust 有：

- `Bsp`；
- `Communication`；
- `Device`；
- `Modules`；
- `Algorithm`；
- `Interaction`。

但真正的依赖关系仍然要沿着代码阅读。

目录能提示功能位置。

它不能完全阻止上层直接依赖底层细节。

#### 设备拓扑外置能力较弱

电机 ID、CAN 实例、对象成员和业务归属通常在具体工程中直接写出。

换一台机器人时，往往需要重新整理：

- `Robot` 成员；
- 设备初始化；
- 回调分发；
- 任务关系；
- 跨模块策略。

#### 不适合直接作为跨项目框架

Dust 的代码非常适合当前哨兵。

但如果直接拿它作为新项目框架，新的机器人通常需要大量改造整机对象和业务链。

### 6.8 一句话评价

> Dust 是四个项目中最接近“已经打完一台机器人”的工程；它的价值主要在真实整机经验，而不是项目级抽象。

## 七、tflm：项目装配型平台骨架

### 7.1 定位

当前 `tflm` 的目标已经不只是“把一台机器人做出来”。

它正在尝试把以下内容拆成稳定边界：

```text
drivers
modules
algorithm
topic
project
```

其中：

- `drivers` 提供底层硬件接口；
- `modules` 组合具体设备；
- `algorithm` 提供纯计算能力；
- `topic` 提供线程间数据契约；
- `project` 负责把这些能力装配成具体项目。

它的核心思想可以概括为：

```text
框架层负责沉淀通用能力。

项目层负责选择能力、绑定板卡、组织线程和实现业务。
```

### 7.2 当前项目边界

`project/README.md` 和 `project/ARCHITECTURE.md` 明确把项目拆成三部分：

```text
project/
├── apps/
├── boards/
└── thread/
```

#### `project/apps`

负责：

- 系统入口；
- 初始化编排；
- 中断处理。

#### `project/boards`

负责：

- DTS overlay；
- 板级 Kconfig；
- 烧录脚本；
- 板型绑定。

#### `project/thread`

负责：

- RTOS 线程；
- 业务线程；
- 线程装配；
- 线程所需模块和 topic 的选择。

这个边界与 COD_H7 的 `USER/Application/Task` 不同。

COD_H7 的任务目录是单个工程内部的功能目录。

`tflm` 的 `project/thread` 则被定义成项目单元的一部分。

### 7.3 真实入口和启动链

当前 `src/main.c` 很简单：

```text
main()
  -> System_Startup()
  -> 循环休眠
```

真正的启动组织在：

```text
project/apps/Init_entry.cpp
```

当前 `System_Startup()` 的实际阶段顺序是：

```text
Bsp
  -> ThreadEarly
  -> Module
  -> ThreadMid
  -> ThreadLate
```

需要特别注意：

`InitStage` 枚举的声明顺序与 `StageMap` 的执行顺序不是简单按枚举数值遍历。

当前真正决定执行顺序的是 `System_Startup()` 中显式调用的 `RunStage()` 顺序。

因此文档和代码都应以真实启动链为准：

```text
RunStage(Bsp)
RunStage(ThreadEarly)
RunStage(Module)
RunStage(ThreadMid)
RunStage(ThreadLate)
```

### 7.4 注册式初始化

线程或模块可以在自己的源文件中声明：

```cpp
REGISTER_INIT(thread_init,  Module,     Mid,  "xxx_init");
REGISTER_INIT(thread_start, ThreadLate, Mid,  "xxx_start");
```

宏会生成 `InitEntry` 并放入：

```text
.user_init
```

链接脚本：

```text
cmd/linker/tflm_init.ld
```

负责提供：

```text
__user_init_start
__user_init_end
```

启动器遍历这段内存，选择当前阶段的注册项并执行。

这条链可以画成：

```text
线程源文件
    -> REGISTER_INIT()
    -> .user_init
    -> tflm_init.ld
    -> __user_init_start / __user_init_end
    -> Init_entry.cpp
    -> RunStage()
```

这与 COD_H7 的集中式 `MX_FREERTOS_Init()` 有本质差异。

COD_H7 的任务创建点集中在一个文件。

`tflm` 的初始化项可以在本地声明，再由统一启动器按阶段执行。

### 7.5 初始化失败策略

`Init_entry.cpp` 还定义了初始化等级：

```text
High
Mid
Low
```

当前策略是：

| 初始化等级 | 当前失败行为 |
| --- | --- |
| `High` | 报错并挂起系统 |
| `Mid` | 报错后继续 |
| `Low` | 警告后继续 |

这比传统工程中所有初始化失败都进入同一个 `Error_Handler()` 更有表达力。

它允许不同组件声明不同的重要性。

例如：

- 核心总线不可用，可以停止；
- 可选传感器不可用，可以继续；
- 实验线程失败，可以只告警。

当前实现仍然比较早期。

但它已经把“初始化失败怎么办”从隐含行为提升成了框架概念。

### 7.6 Kconfig、CMake 和项目装配

根 `CMakeLists.txt` 做了几件关键事情：

1. 选择活动项目；
2. 选择板级 overlay；
3. 选择板级 `.conf`；
4. 选择板级 `board.cmake`；
5. 加载 Zephyr；
6. 按配置加入框架层和项目层。

当前根 CMake 中有：

```cmake
set(ACTIVE_PRJ "test")
set(PROJ_DIR project)
set(CONFIG_SYM PRJ_TEST)
```

项目配置打开后，才会加入：

```text
drivers
algorithm
modules
topic
cmd
project
```

`project/thread/Kconfig` 继续把线程和依赖串起来。

例如：

```text
TRD_CHASSIS
    -> MOD_CTL_POWER
    -> MOD_DEV_MOTOR_DJI
    -> TPC_TO_CAN_TX
    -> TPC_REMOTE_TO
```

```text
TRD_IMU
    -> MOD_DEV_IMU
    -> TPC_IMU_TO
```

```text
TRD_CAN_TX
    -> COM_CAN
    -> TPC_TO_CAN_TX
```

这条链表达的是：

```text
启用线程
    -> 自动选择依赖模块
        -> 自动选择驱动、算法或 topic
```

COD_H7 主要依靠目录和 CMake 源文件收集。

`tflm` 则开始把功能依赖写进配置系统。

### 7.7 drivers 层

`drivers/ARCHITECTURE.md` 定义的驱动层职责是：

```text
封装 Zephyr 设备驱动 API
对外提供统一 C++ 接口
```

当前目录包括：

```text
drivers/
├── communication/
│   ├── can/
│   ├── spi/
│   ├── uart/
│   ├── rs485/
│   ├── usb/
│   └── stream/
└── device/
    ├── gpio/
    └── pwm/
```

文档明确要求驱动层：

- 不包含业务逻辑；
- 不依赖 `modules`；
- 不依赖 `algorithm`；
- 不依赖 `topic`；
- 不创建线程；
- 不直接反向依赖项目层。

这是一条比 COD_H7 更明确的底层边界。

### 7.8 modules 层

`modules` 负责具体设备管理器和设备协议。

当前包含：

```text
modules/
├── imu/
├── motors/
├── powermeter/
└── remotes/
```

模块可以组合：

```text
drivers
    + algorithm
        -> 具体设备模块
```

例如 IMU 模块可以组合：

- SPI；
- GPIO；
- PWM；
- 加热控制；
- 滤波；
- 姿态算法。

电机模块可以组合：

- CAN 驱动；
- 电机协议；
- PID 或控制接口。

模块层的关键规则是：

```text
模块负责设备能力。

项目线程负责把多个模块组合成业务。
```

### 7.9 algorithm 层

`algorithm` 被定义为纯计算层。

当前包含：

```text
controller/
    PID
    power_ctrl
    timer

filter/
    LPF
    HPF
    Kalman
    Quaternion EKF

identify/
    RLS
    motor model

tflm/
    TensorFlow Lite Micro
```

它不应该：

- 创建线程；
- 持有硬件句柄；
- 直接操作 PWM；
- 直接依赖模块；
- 直接依赖项目。

这使算法可以被多个线程或多个项目复用。

### 7.10 topic 层

`topic` 负责线程间数据通道。

当前通道包括：

```text
imu_to
remote_to
to_can_tx
```

其中：

- `imu_to` 使用 zbus；
- `remote_to` 使用 zbus；
- `to_can_tx` 使用 `k_msgq`。

它们的职责是定义：

- 消息结构；
- 通道声明；
- 观察者；
- 消息队列；
- 线程间数据契约。

topic 不应该：

- 持有设备实例；
- 创建业务线程；
- 直接实现控制逻辑。

这使数据结构和数据传输机制可以从具体线程中独立出来。

### 7.11 当前线程的真实组织

当前线程代码展示了一个比较清晰的模式。

#### CAN 发送线程

`project/thread/can/trd_can_tx.cpp`：

```text
thread_init()
    -> 获取 devicetree alias
    -> 检查 CAN 设备 ready
    -> 初始化 CAN
    -> 注册 RX 回调

thread_start()
    -> 创建 CAN TX 线程
```

CAN TX 线程从 `k_msgq` 取出待发送消息，再调用驱动发送。

#### IMU 线程

`project/thread/imu/trd_imu.cpp`：

```text
thread_init()
    -> imu_.Init()

thread_start()
    -> imu_.Start()
```

IMU 设备和算法细节由 `modules/imu` 管理。

线程文件主要负责：

- 声明局部实例；
- 选择启动模式；
- 注册初始化项。

#### 底盘线程

`project/thread/chassis/trd_chassis.cpp` 的控制链是：

```text
读取遥控器
    -> 运动学解算
    -> 优劣弧调整
    -> 角度/速度/力矩控制
    -> 功率预测和分配
    -> 组帧
    -> 发布到 CAN TX 消息队列
```

这个线程是当前 `tflm` 中已经比较完整的业务线程。

它组合：

- `remote_to`；
- DJI 电机模块；
- PID；
- 功率控制；
- `to_can_tx`；
- CAN 发送线程。

#### 云台线程

`project/thread/gimbal/trd_gimbal.cpp` 的链路是：

```text
读取遥控器 zbus
    -> 更新云台目标角
    -> 读取电机反馈
    -> 位置环
    -> 速度环
    -> MIT 控制帧
    -> 发布到 gimbal_tx 队列
```

这说明当前 `tflm` 已经不仅是抽象目录。

它已经在用公共层组织真实控制链。

### 7.12 tflm 的优势

#### 项目层和框架层分离

最重要的边界是：

```text
框架层：
    drivers
    modules
    algorithm
    topic

项目层：
    project/apps
    project/boards
    project/thread
```

框架层不应该依赖项目层。

项目层可以组合框架层。

这为新项目迁移提供了清晰的默认落点。

#### 编译期裁剪能力更强

Kconfig 可以表达：

- 是否启用某个线程；
- 某个线程需要哪些模块；
- 某个模块需要哪些驱动；
- 某个 topic 是否进入编译。

CMake 再根据配置选择源文件。

这比固定 `freertos.c` 更适合多个项目共用一棵代码树。

#### 初始化可以本地注册

线程不需要把所有初始化函数集中复制到一个总入口。

它可以在本地声明：

```text
thread_init
thread_start
```

再通过阶段和等级参与统一启动。

#### 数据契约已经开始独立

`topic` 让遥控器、IMU 和 CAN 输出不必都通过全局结构体直接耦合。

这为后续增加：

- 多发布者；
- 数据观察；
- 缓存；
- 线程解耦；

留下了空间。

#### Demo 和正式业务有明确入口

`project/thread/test` 可以用于：

- 设备验证；
- 参数实验；
- 快速 Demo；
- 临时功能；
- 辨识流程。

实验完成后，再把稳定能力沉淀回算法、模块、topic 或正式线程。

### 7.13 tflm 的局限

#### 当前仍处于收敛阶段

代码、文档和注释并不一定全部同步。

阅读时必须以 live tree 为准。

尤其需要注意：

- 旧文档可能使用 `projects/`；
- 当前真实目录是 `project/`；
- 旧启动描述可能落后于 `Init_entry.cpp`；
- 初始化阶段的实际顺序应看 `System_Startup()`。

#### 抽象层次高，首次学习成本更高

阅读一个功能可能需要经过：

```text
Kconfig
    -> CMake
    -> driver
    -> module
    -> topic
    -> thread
    -> init registration
    -> board overlay
```

这比在 COD_H7 中直接打开 `bsp_can.c` 和 `Control_Task.c` 更慢。

#### 项目装配规则还需要继续固化

虽然 `project/` 边界已经明确，但仍然需要继续完善：

- 项目入口规范；
- board 配置约束；
- 多项目切换；
- 初始化依赖检查；
- 线程和模块的生命周期；
- 失败后的降级语义。

#### 真实整机闭环仍在发展

当前已经有：

- IMU；
- 遥控；
- CAN；
- 底盘；
- 云台；
- 功率控制；
- TFLM 实验入口。

但它和 Dust 一样完整的整机策略仍然需要持续装配。

### 7.14 一句话评价

> `tflm` 当前最重要的变化，是把“项目应该修改哪里”从作者经验变成了 `project/`、Kconfig、CMake 和初始化注册共同表达的结构规则。

## 八、运行时启动模型对比

### 8.1 四种启动链

| 项目 | 启动组织方式 |
| --- | --- |
| `basic_framework-master` | 顶层机器人初始化集中编排，再创建基础任务 |
| `COD_H7` | `main.c` 调 HAL 和 BSP，再由 `MX_FREERTOS_Init()` 创建固定任务 |
| Dust | CubeMX/FreeRTOS 启动后，由对象 `Init()` 分散创建对象任务 |
| `tflm` | `main.c` 调 `System_Startup()`，遍历链接段中的注册项，按阶段执行 |

### 8.2 集中式初始化

`basic_framework-master` 和 COD_H7 都更偏集中式。

集中式的典型特点是：

```text
一个入口文件
    -> 一串明确调用
        -> 创建所有任务
```

优点：

- 顺序清楚；
- 调试入口简单；
- 新人容易找到任务清单；
- 适合固定硬件和固定机器人。

缺点：

- 初始化文件容易变长；
- 新增功能需要改中央入口；
- 项目差异容易继续堆到中央文件；
- 初始化依赖更多由阅读者记忆维护。

### 8.3 对象分散式初始化

Dust 把初始化责任放入对象。

典型模式是：

```text
robot_.Init()
    -> chassis_.Init()
        -> 创建 chassis task
    -> gimbal_.Init()
        -> 创建 gimbal task
```

优点：

- 对象的状态、接口和任务靠在一起；
- 设备模块更容易作为一个整体搬动；
- 复杂整机业务表达直观。

缺点：

- 系统任务清单不再集中；
- 很难只看一个文件了解所有任务；
- 初始化顺序可能分散在多个类；
- 任务优先级和资源关系需要全局检查。

### 8.4 注册式初始化

`tflm` 把初始化项变成编译期可收集的记录：

```text
InitEntry
    = func + stage + level + name
```

这种模型的优点是：

- 初始化项可以和功能源文件放在一起；
- 启动器统一控制阶段；
- 可以统一打印初始化名称；
- 可以统一处理失败等级；
- 新增模块不必不断修改中央列表。

它的代价是：

- 需要理解链接段；
- 需要理解 `KEEP()`；
- 初始化顺序不再完全由源文件排列决定；
- 注册项过多时，必须维护阶段语义。

### 8.5 哪种模型更好

不能脱离项目目标回答。

固定单板模板中，COD_H7 的集中式任务创建很合适。

具体机器人中，Dust 的对象任务很高效。

队伍基础框架中，basic 的集中编排和消息中心比较容易传承。

跨项目平台中，tflm 的注册式启动更有扩展空间。

更准确的结论是：

```text
固定系统：
    集中式初始化更容易调试

复杂整机：
    对象内聚式初始化更容易落地

多项目平台：
    注册式初始化更容易扩展
```

### 8.6 tflm 当前启动链需要继续明确的地方

当前代码已经有阶段：

```text
Bsp
ThreadEarly
Module
ThreadMid
ThreadLate
```

但阶段命名和实际执行语义仍需持续统一。

例如：

- `ThreadEarly` 在 `Module` 之前；
- CAN TX 线程可以先于设备模块启动；
- 模块初始化和线程启动分开；
- `ThreadMid`、`ThreadLate` 的依赖规则要继续文档化。

阶段越多，越需要说明：

```text
某个阶段解决什么依赖？
谁可以注册到这个阶段？
失败后系统还能否运行？
```

## 九、编译期装配与配置裁剪对比

### 9.1 basic_framework-master

它主要依靠：

- 目录；
- 宏；
- `robot_def.h`；
- 工程文件；
- 人工注册；
- 文档约定。

这种方式成熟且直接。

但项目差异没有被完全抽象成独立项目单元。

### 9.2 COD_H7

COD_H7 的根 CMake 主要做三件事：

1. 加入 CubeMX 子目录；
2. 使用 `GLOB_RECURSE` 收集 `USER` 源文件；
3. 链接 HAL、FreeRTOS、USB 和 ARM DSP。

核心关系可以表示为：

```text
Core/Src
    + USER/BSP/Src
    + USER/Components/*/Src
    + USER/Application/Task/Src
        -> 一个固定可执行文件
```

这种方式的优点是简单。

目录中的源文件默认都会进入工程。

但它没有表达：

- 某个任务开关；
- 某个设备模块依赖；
- 某个算法是否裁剪；
- 某个项目选择什么硬件拓扑。

### 9.3 Dust

Dust 更偏完整工程编译。

典型迁移方式是：

```text
复制工程
    -> 改板级配置
    -> 改设备对象
    -> 改 CAN ID
    -> 改 Robot
    -> 改业务策略
```

它的构建边界服务于一台机器人。

因此工程复制并不是缺点。

它只是说明复用单位是：

```text
一个完整整机工程
```

而不是：

```text
一个框架加一个项目配置
```

### 9.4 tflm

`tflm` 的配置链是：

```text
板卡
    -> overlay
    -> board.conf
    -> board.cmake

项目
    -> PRJ_TEST
    -> project/

线程
    -> project/thread/Kconfig
    -> project/thread/CMakeLists.txt

依赖
    -> drivers/modules/algorithm/topic Kconfig
    -> select

源码
    -> 按 CONFIG_* 选择加入
```

这套链路的价值在于：

```text
“是否启用”变成配置问题。
“需要什么”变成依赖问题。
“属于哪个项目”变成 project 问题。
```

### 9.5 配置驱动带来的实际收益

以 `TRD_CHASSIS` 为例：

```text
启用 TRD_CHASSIS
    -> 启用功率控制
    -> 启用 DJI 电机
    -> 启用 CAN TX topic
    -> 启用遥控 topic
```

如果关闭 `TRD_CHASSIS`：

- 底盘线程源文件不加入；
- 相关模块可以不选；
- 相关 topic 可以不编译；
- 其他项目不会被底盘业务污染。

这是 COD_H7 通过固定目录和手工注释很难自然表达的能力。

### 9.6 tflm 当前还需要补强的地方

配置驱动不等于配置已经完美。

还需要继续明确：

- 活动项目的切换机制；
- 多项目共存时的配置命名；
- 同一模块被多个线程选择时的资源所有权；
- 一个硬件总线由多个模块共享时的生命周期；
- 配置冲突如何在 Kconfig 阶段失败；
- 项目板级配置和框架驱动默认配置的优先级。

## 十、模块、任务和数据通信对比

### 10.1 四种数据组织模型

| 项目 | 主要数据组织方式 |
| --- | --- |
| `basic_framework-master` | 模块实例 + message center |
| `COD_H7` | 全局结构体、全局数组、任务直接调用 |
| Dust | C++ 对象成员 + Robot 直接协调 |
| `tflm` | 模块对象 + topic + 线程局部实例 |

### 10.2 basic 的消息契约

basic 的应用边界通过 topic 维持。

优点：

- 应用不必互相包含；
- 命令和反馈有明确结构；
- 多人可以按应用边界开发；
- 可以替换具体实现。

代价：

- 消息结构需要维护；
- 话题注册需要维护；
- 数据延迟和队列语义需要理解；
- 调试时需要多跳几层。

### 10.3 COD_H7 的全局状态

COD_H7 的典型路径：

```text
中断回调
    -> 全局设备数组
        -> 任务直接读取
            -> 全局控制结构
                -> 另一个任务读取
```

这种方式对固定单板十分高效。

特别适合：

- 设备数量少；
- 任务数量固定；
- 数据更新周期明确；
- 维护者熟悉整个工程。

当数据来源增加时，问题会逐渐出现：

- 谁最后写了这个字段？
- 这个结构体是否正在被另一个任务读取？
- 这次数据是新帧还是旧帧？
- 是否需要临界区？
- 是否需要复制快照？

### 10.4 Dust 的对象直连

Dust 的数据不是完全依靠全局变量。

它更多通过对象成员保存状态。

例如：

```text
robot_.chassis_
robot_.gimbal_
robot_.reload_
robot_.mcu_comm_
```

对象直连比散落的全局数组更有所有权感。

但跨模块决策集中到了 `Robot::Task()`。

因此它解决的是：

```text
设备状态属于哪个对象？
```

而不是完全解决：

```text
模块之间如何通过契约解耦？
```

### 10.5 tflm 的 topic + 模块 + 线程

当前 `tflm` 尝试把三件事分开：

```text
modules
    保存设备能力和设备状态

topic
    定义线程之间传什么

project/thread
    决定什么时候读、怎么组合、如何控制
```

例如底盘线程：

```text
remote_to
    -> 读取遥控数据

DJI motor module
    -> 读取电机反馈和设置目标

power_ctrl
    -> 进行功率预测和分配

to_can_tx
    -> 发布 CAN 输出

can thread
    -> 统一发送
```

它把“设备能力”和“业务周期”拆开了。

### 10.6 zbus 和 k_msgq 的区别

当前 topic 层没有强行使用一种通信机制。

`imu_to` 和 `remote_to` 使用 zbus，适合发布和订阅。

`to_can_tx` 使用 `k_msgq`，适合多个控制线程向一个 CAN 发送线程提交帧。

这是一个重要判断：

```text
不同的数据关系可以使用不同的通道语义。
```

zbus 更适合：

- 状态广播；
- 一个模块发布；
- 多个模块观察；
- 读写结构化消息。

`k_msgq` 更适合：

- 点对点；
- 多个生产者；
- 一个消费者；
- 每条消息都应独立保留。

### 10.7 当前 tflm 需要注意的通信问题

消息通道虽然比全局变量清晰，但仍然需要定义：

- 消息是状态还是事件；
- 新数据是否覆盖旧数据；
- 队列满时丢弃还是阻塞；
- 发布者是否允许多个；
- 订阅者是否能得到最新快照；
- 时间戳由谁提供；
- 失联状态由谁判断。

尤其是控制链中：

```text
遥控 -> 底盘 -> CAN
```

需要区分：

```text
遥控状态
    适合取最新值

CAN 控制帧
    可能需要保留每条发送请求
```

当前 `to_can_tx` 使用消息队列是合理方向。

但队列满时的丢帧策略也应持续文档化。

## 十一、硬件抽象与设备拓扑对比

### 11.1 basic 的实例模型

basic 更接近 C 风格实例注册：

```c
DJIMotorInstance *motor = DJIMotorInit(&config);
DJIMotorSetRef(motor, target);
```

这种模型的优点：

- 多个相同设备可以统一创建；
- 配置结构体可以表达差异；
- BSP 可以通过实例和回调找到模块；
- 模块不必写死某个具体对象名。

### 11.2 COD_H7 的全局数组模型

COD_H7 直接定义具体设备数组：

```text
Chassis_Motor[4]
DM_8009_Motor[4]
```

CAN 回调也直接遍历这些数组。

这种方式对固定拓扑很方便。

但是设备拓扑和板级回调绑定较深。

如果从四个底盘电机改成：

- 两个舵轮；
- 六个麦轮；
- 两个不同 CAN 总线；
- 混合 DJI/DM 电机；

通常需要同时修改：

- Motor 数组；
- CAN 回调；
- CAN 发送帧；
- Control 任务；
- CAN 任务；
- 参数配置。

### 11.3 Dust 的对象所有权模型

Dust 更强调设备属于哪个功能对象：

```text
chassis_
    -> motor_chassis_1_
    -> motor_chassis_2_
    -> ...

gimbal_
    -> motor_yaw_
    -> motor_pitch_
```

这种模型表达力很强。

设备属于底盘。

底盘拥有设备。

底盘任务使用设备。

但具体 CAN ID 和对象成员仍然是整机工程的一部分。

### 11.4 tflm 的驱动、模块和项目组合

`tflm` 尝试把关系拆成：

```text
devicetree
    -> drivers
        -> modules
            -> project/thread
```

例如：

```text
板级 CAN alias
    -> Can driver
        -> DJI motor module
            -> chassis thread
```

IMU 也可以表示为：

```text
板级 SPI/GPIO/PWM
    -> SPI/GPIO/PWM drivers
        -> BMI088/ICM42688 module
            -> IMU thread
```

这样，硬件绑定更多落到：

- DTS；
- overlay；
- board conf；
- 模块配置；
- 项目线程实例。

这比把引脚和设备拓扑全部写进单个 `bsp_xxx.c` 更容易跨板卡。

### 11.5 抽象不是越多越好

硬件抽象要有边界。

如果只是为一个固定寄存器操作增加三层包装，可能会降低调试效率。

当前四个项目的合理取舍分别是：

- basic：用实例模型换复用；
- COD_H7：用直接全局对象换单板效率；
- Dust：用对象所有权换整机表达力；
- tflm：用驱动、模块和项目分层换跨项目迁移。

## 十二、复用、移植与维护成本对比

### 12.1 新增一台相近机器人时，分别要改什么

#### basic_framework-master

通常保留：

```text
bsp
module
message_center
```

主要修改：

```text
application
robot_def.h
参数和板卡配置
```

它的复用单位是：

```text
框架底座 + 新 application
```

#### COD_H7

通常保留：

```text
HAL
BSP
Components
FreeRTOS
CMake
```

主要修改：

```text
CubeMX 外设配置
Motor 数组和 ID
UART 用途
任务逻辑
控制参数
```

它的复用单位是：

```text
H7 单板模板 + 新业务代码
```

#### Dust

通常需要：

```text
复制整机工程
重新组织 Robot 成员
重新设置设备拓扑
重新设置 CAN ID
修改整机策略
```

它的复用单位是：

```text
完整机器人工程
```

#### tflm

在框架能力已经覆盖需求的前提下，原则上主要修改：

```text
project/apps
project/boards
project/thread
```

框架层尽量保持：

```text
drivers
modules
algorithm
topic
```

这正是 `tflm` 当前最重要的架构目标。

### 12.2 迁移成本的来源

迁移成本不只是文件数量。

主要来自以下四类绑定：

1. 硬件绑定；
2. 设备拓扑绑定；
3. 任务装配绑定；
4. 业务策略绑定。

COD_H7 的硬件绑定较强。

Dust 的设备拓扑和业务策略绑定较强。

basic 的规则和消息边界较强，但底层平台绑定较强。

tflm 试图把四类绑定分别放入：

```text
硬件绑定
    -> project/boards + DTS

设备拓扑绑定
    -> project/thread 实例和配置

任务装配绑定
    -> project/thread + REGISTER_INIT

业务策略绑定
    -> project/thread
```

### 12.3 维护者如何找到新代码应该放在哪里

一个好的框架应该能回答：

```text
我现在要加一个新东西，应该放哪？
```

四个项目的默认回答不同。

#### basic

先判断是：

- BSP；
- module；
- app；
- message。

#### COD_H7

先判断是：

- BSP；
- Device；
- Algorithm；
- Controller；
- Task。

但如果一个功能跨越多个层，边界需要靠开发者自己判断。

#### Dust

先判断它属于：

- 某个设备对象；
- 某个功能对象；
- `Robot` 总控；
- 通信分发；
- 算法。

#### tflm

先判断：

- 是纯计算吗？放 `algorithm`；
- 是具体设备管理吗？放 `modules`；
- 是硬件接口吗？放 `drivers`；
- 是线程间数据吗？放 `topic`；
- 是项目装配或业务周期吗？放 `project/thread`；
- 是板卡绑定吗？放 `project/boards`；
- 是启动编排吗？放 `project/apps`。

这套判断规则是 tflm 的长期价值之一。

### 12.4 当前维护成本的真实取舍

`COD_H7` 的查找成本低。

但边界维护成本会随着项目变大而上升。

`tflm` 的查找成本高。

但如果边界稳定，长期维护成本可能下降。

所以两者不是简单的：

```text
简单 vs 复杂
```

而是：

```text
前期查找成本
    vs
后期边界维护成本
```

## 十三、整机业务闭环能力对比

### 13.1 业务闭环的判断标准

本文把整机闭环拆成八个环节：

1. 输入；
2. 设备采集；
3. 状态估计；
4. 目标生成；
5. 控制计算；
6. 输出通信；
7. 故障保护；
8. 跨模块策略。

### 13.2 basic_framework-master

basic 已经具备比较成熟的机器人应用组织：

```text
输入
    -> robot_cmd
    -> 发布底盘/云台/发射命令

底盘/云台/发射
    -> 读取命令
    -> 控制对应设备
    -> 发布反馈

robot_cmd
    -> 读取反馈
```

它的闭环能力来自：

- app 组织；
- module 复用；
- message center；
- 多板切换；
- 任务频率和文档规则。

它比 COD_H7 更接近完整队伍工程。

### 13.3 COD_H7

COD_H7 当前快照更偏“控制骨架”：

```text
遥控器
    -> remote_ctrl
    -> Control_Task
    -> Chassis_PID
    -> Control_Info
    -> CAN_Task
    -> FDCAN 输出
```

IMU 链路是：

```text
BMI088
    -> INS_Task
    -> LPF
    -> Quaternion EKF
    -> INS_Info
```

电机反馈链路是：

```text
FDCAN RX
    -> Motor_Info_Update
    -> Chassis_Motor / DM_8009_Motor
    -> Control_Task 或 CAN_Task
```

这些链路已经具备真实控制开发价值。

但当前任务和业务仍然比较模板化。

例如：

- `Detect_Task` 主要做遥控监测；
- `Control_Task` 主要展示底盘速度控制；
- `CAN_Task` 组织电机使能和发送；
- 任务间没有完整的整机模式协调。

因此它不能仅因为硬件能力完整，就被称为整机框架。

### 13.4 Dust

Dust 的闭环完整度最高。

它已经把输入、设备状态、控制和整机策略都连接起来：

```text
遥控器 / 视觉 / 裁判系统
            ↓
       Robot::Task()
        ↓    ↓    ↓
     Gimbal Chassis Reload
        ↓    ↓    ↓
       CAN / 电机 / 外部设备
```

它的业务策略不是留在模板中等待实现。

而是已经进入：

- 模式判断；
- 目标生成；
- 设备控制；
- 保护处理；
- 跨模块协调。

因此 Dust 的整机评分最高。

### 13.5 tflm

当前 `tflm` 已经形成多个真实业务链：

```text
遥控器
    -> remote topic
    -> chassis/gimbal
    -> CAN TX topic
    -> CAN thread
    -> CAN driver
```

```text
IMU driver
    -> IMU module
    -> IMU thread
    -> imu topic
```

```text
底盘
    -> 运动学
    -> 串级 PID
    -> 功率控制
    -> CAN 输出
```

这说明它已经具备真正的控制业务。

但与 Dust 的差异是：

- tflm 更关注公共模块和项目装配；
- Dust 更关注整机策略的集中闭环；
- tflm 的复杂机器人模式还在逐步形成；
- Dust 已经围绕一台机器把策略压实。

所以当前 tflm 不是业务能力弱。

而是它的架构目标更偏平台，当前具体机器人仍在建设中。

### 13.6 一个重要结论

不能使用“平台化排名”去否定 Dust 的整机价值。

也不能使用“整机闭环排名”去否定 tflm 的平台价值。

这两个维度必须分开。

## 十四、按不同目标分别评分

### 14.1 评分方法

每项满分 20 分。

分数只用于表达当前代码快照下的相对位置。

它不是项目绝对质量认证。

### 14.2 框架架构能力评分

| 项目 | 运行时基础 | 职责边界 | 项目迁移 | 维护传承 | 业务闭环 | 总分 |

| `COD_H7` | 16 | 15 | 13 | 14 | 16 | **74** |

### 14.3 为什么 tflm 得分最高

#### 运行时基础

它站在 Zephyr、Kconfig、CMake、DTS 和 zbus 等基础上。

#### 职责边界

`drivers`、`modules`、`algorithm`、`topic`、`project` 已经形成比较明确的职责划分。

#### 项目迁移

在公共能力足够的前提下，新项目主要修改：

```text
project/apps
project/boards
project/thread
```

#### 维护传承

入口、注册项、配置、线程和公共层都有文档化趋势。

#### 没有拿满分的原因

当前仍存在：

- 文档和代码未完全同步；
- 初始化阶段语义还在收敛；
- 多项目装配机制仍需完善；
- 整机业务闭环还没有达到 Dust 的完整度。

### 14.4 为什么 basic 得分第二

它的平台化能力已经成熟。

尤其在：

- `bsp/module/app`；
- message center；
- 多机器人；
- 文档；
- 队伍传承；

方面非常强。

分数没有超过 tflm，主要因为：

- 底层绑定 STM32/HAL/FreeRTOS；
- 项目差异没有完全收敛到独立项目层；
- 编译期裁剪能力相对弱；
- 部分规则仍然依赖宏和人工纪律。

### 14.5 为什么 COD_H7 居中

它比普通 CubeMX 工程强很多。

它已经有：

- BSP；
- Device；
- Controller；
- Algorithm；
- Task；
- CMake；
- CLion；
- Ninja；
- 完整 H7 外设。

但它的主要边界仍是：

```text
功能目录 + 全局状态 + 固定任务
```

还没有形成：

- 项目层；
- topic 契约；
- Kconfig 依赖；
- 注册式启动；
- 多板卡配置模型。

### 14.6 为什么 Dust 框架分较低但业务分最高

Dust 的整机闭环不是问题。

它的问题是复用边界主要围绕当前机器人：

- Robot 成员；
- CAN ID；
- 设备拓扑；
- 任务创建；
- 总控策略。

这些都服务于一台具体机器。

因此它是非常强的产品工程。

但不是以跨项目平台为第一目标的框架。

### 14.7 单台比赛整机评分

| 项目 | 单台比赛整机分 | 主要原因 |
| --- | ---: | --- |
| `Dust_SentinelRobot_L_Game` | **95** | 整机对象、设备链和业务策略完整 |
| `basic_framework-master` | **88** | app/module 底座成熟，业务组合能力强 |
| 当前 `tflm` | **82** | 公共层和控制链已成形，整机策略仍在装配 |
| `COD_H7` | **76** | 单板外设和控制骨架完整，业务闭环较轻 |

### 14.8 单板快速启动评分

如果目标是“今天拿到一块板，尽快验证外设和基础控制”，排序可以是：

```text
COD_H7
    >
Dust
    >
basic_framework-master
    >
tflm
```

原因：

- COD_H7 的 CubeMX 外设和 BSP 已经准备好；
- Dust 的具体设备对象和通信链路很直接；
- basic 需要理解更多框架规则；
- tflm 需要先理解 board、Kconfig、thread 和初始化装配。

### 14.9 跨项目迁移评分

如果目标是“保留公共能力，快速新建另一个项目”，排序是：

```text
tflm
    >
basic_framework-master
    >
COD_H7
    >
Dust
```

但这里有一个前提：

```text
tflm 的框架层能力必须已经覆盖新项目需求。
```

如果新项目需要一个全新的芯片驱动，仍然需要补：

- Zephyr board；
- DTS；
- driver；
- module；
- project 装配。

## 十五、tflm 应该吸收什么，以及还要补什么

### 15.1 应该吸收 basic 的内容

#### 吸收边界意识

继续坚持：

```text
框架层不依赖项目层。
```

#### 吸收消息契约意识

当前已有 zbus 和 `k_msgq`。

还应继续明确：

- 消息是状态还是事件；
- 消息更新频率；
- 消息所有权；
- 队列满时策略；
- 失联判定；
- 时间戳语义。

#### 吸收文档和传承意识

每个层都应有：

- 职责；
- 不负责什么；
- 调用方；
- 被谁调用；
- 一个最小示例；
- 一个真实路径。

### 15.2 应该吸收 COD_H7 的内容

#### 吸收板级能力清单

COD_H7 对一块 H7 控制板常见能力的覆盖很完整。

tflm 可以继续积累：

- CAN；
- UART DMA；
- SPI；
- USB；
- PWM；
- ADC；
- IMU；
- 电机；

的板级适配和验证入口。

#### 吸收快速联调路径

COD_H7 的数据链路短。

tflm 在保留层次的同时，也要保证：

```text
收到一帧数据后，能够快速定位到模块和线程。
```

#### 吸收 CMake 工具链意识

COD_H7 已经使用：

- CMake；
- Ninja；
- compile commands；
- CLion；
- ARM DSP。

tflm 需要继续保持命令行、编辑器和构建系统的一致性。

### 15.3 应该吸收 Dust 的内容

#### 吸收整机对象拓扑的直观性

虽然 tflm 不必复制一个巨大的 `Robot` 总控，但仍然需要让读者知道：

```text
当前项目由哪些设备和线程组成？
```

这个问题可以通过：

- 项目架构文档；
- thread 实例表；
- topic 数据流图；
- 设备拓扑表；

来回答。

#### 吸收跨模块策略意识

完全拆成消息以后，跨模块策略可能变得分散。

tflm 需要为项目层保留一个明确的策略组织位置。

这个位置可以是：

- 项目级协调线程；
- 状态机；
- 行为管理器；
- 整机策略模块。

不一定要把所有策略重新塞回一个 `Robot::Task()`。

但也不能让复杂策略分散在多个线程里无法追踪。

#### 吸收实时闭环意识

控制热路径应该保持直线：

```text
输入
    -> 目标
    -> 控制
    -> 限幅
    -> 输出
```

消息和抽象不能让核心 1 ms 控制路径变得不可读。

### 15.4 tflm 还应该继续补的内容

#### 项目模板

应该让新建项目有最小模板：

```text
project/
├── apps/
├── boards/
└── thread/
```

并明确：

- 必须文件；
- 可选文件；
- 默认启动项；
- 最小 board 配置；
- 最小线程配置。

#### 初始化依赖检查

注册式初始化需要更清楚地表达：

- 同一阶段内是否有顺序要求；
- 一个线程依赖哪个模块；
- 模块失败后哪些线程不能启动；
- High/Mid/Low 的实际使用约定。

#### 设备拓扑配置

当前一些设备 ID 和参数仍然写在具体线程中。

后续可以把稳定的拓扑信息进一步抽到：

- board config；
- project config；
- 设备配置结构体；
- 单独的 project 参数文件。

#### 线程生命周期

需要继续统一：

- `thread_init()` 的职责；
- `thread_start()` 的职责；
- `Start()` 失败怎么办；
- 线程是否允许重复启动；
- 线程停止和重启是否支持；
- 模块 ready 与线程 ready 如何区分。

#### 故障和失联语义

需要统一：

- CAN 设备未 ready；
- 电机失联；
- 遥控器超时；
- IMU 初始化失败；
- topic 数据超时；
- 线程启动失败；

分别属于哪一层处理。

## 十六、把四个项目看成一条成长路径

### 16.1 第一阶段：先学会规则化

`basic_framework-master` 代表的是：

```text
不要只写功能，要先建立边界。
```

它让人看到：

- 目录不是随便分的；
- 任务频率需要约定；
- 应用之间需要通信契约；
- 多机器人需要参数和角色切换；
- 文档本身也是工程能力。

### 16.2 第二阶段：先把单板能力跑通

`COD_H7` 代表的是：

```text
先把一块真实控制板变成可工作的底座。
```

它让人看到：

- 时钟、Cache、MPU；
- DMA；
- 多路 FDCAN；
- UART 空闲线和双缓冲；
- SPI IMU；
- USB；
- PWM；
- FreeRTOS 任务；

这些板级能力如果没有跑通，架构讨论很容易停留在目录层。

### 16.3 第三阶段：完成一台整机

Dust 代表的是：

```text
架构最终要落到真实设备、真实通信和真实策略。
```

它让人看到：

- 设备拓扑不是抽象图；
- CAN ID 需要和对象对应；
- 底盘和云台需要真正控制；
- 上下板、裁判系统和视觉会影响整机策略；
- 总控在比赛工程中有很高价值。

### 16.4 第四阶段：提炼自己的平台语言

`tflm` 代表的是：

```text
不再只是复用别人的框架，而是开始重新定义项目、模块、驱动、算法和通信边界。
```

它试图把前面三类经验拆开吸收：

```text
basic
    -> 分层、消息、文档、传承

COD_H7
    -> 板级能力、CMake、快速联调

Dust
    -> 设备对象、整机控制、实战闭环

tflm
    -> 项目装配、Kconfig、注册式启动、公共层沉淀
```

### 16.5 这不是简单的线性升级

四个项目不是：

```text
旧项目
    -> 新项目
        -> 更高级项目
```

而是四种互相补充的能力：

```text
平台规则
    + 单板底座
    + 整机经验
    + 项目装配
```

真正成熟的框架应该同时拥有：

- basic 的边界和传承；
- COD_H7 的板级覆盖和联调效率；
- Dust 的整机闭环；
- tflm 的项目隔离和配置裁剪。

## 十七、最终结论

### 17.1 四个项目各自最强的地方

#### `basic_framework-master`

最强的是：

```text
把队伍经验变成规则。
```

#### `COD_H7`

最强的是：

```text
把一块 STM32H7 控制板变成可直接开发的单板底座。
```

#### `Dust_SentinelRobot_L_Game`

最强的是：

```text
把设备、任务和策略真正连成一台机器人。
```

#### `tflm`

最强的是：

```text
把项目差异从框架层中抽离，并用配置和注册机制支撑装配。
```

#### 单台比赛整机能力


### 17.3 对当前 tflm 的准确评价

当前 `tflm` 不能简单称为“已经完成的平台”。

更准确的说法是：

> 它已经形成了平台化的主要骨架，正在把板级、设备、算法、通信和项目业务逐步收敛到稳定边界。

它当前最重要的架构成果不是某一个线程。

而是这条关系已经被明确写出来：

```text
drivers
    -> 硬件接口

modules
    -> 设备能力

algorithm
    -> 纯计算

topic
    -> 数据契约

project
    -> 项目装配和业务线程
```

### 17.4 对 COD_H7 的准确评价

COD_H7 也不应被低估。

它不是普通 CubeMX 空工程。

它已经具备：

- 完整 H7 外设底座；
- BSP 分区；
- Device/Controller/Algorithm 组件；
- FreeRTOS 任务骨架；
- CMake/CLion/Ninja 工具链；
- BMI088、DJI、DM、遥控器和 UART DMA 等真实能力。

但它当前的本质仍是：

```text
结构化单板模板
```

而不是：

```text
跨项目配置驱动框架
```

### 17.5 最后一句话

如果只问“哪个最好”，答案没有意义。

更准确的答案是：

- 想要队伍传承，先看 `basic_framework-master`；
- 想从 STM32H7 单板快速开始，先看 `COD_H7`；
- 想学习如何把一台机器人做完整，先看 Dust；
- 想继续发展自己的框架体系，当前 `tflm` 是最值得投入的方向。

四个项目放在一起，呈现的是一条互补的成长路径：

```text
借鉴成熟框架
    -> 整理单板模板
        -> 完成整机闭环
            -> 提炼项目型平台
```
