## 1. 这次改写解决什么问题

旧版路线覆盖的内容很多：

- 芯片架构；
- 启动流程；
- Zephyr；
- 数据结构；
- 编译链接；
- 控制理论；
- 状态估计；
- 通信协议；
- Linux；
- 汇编；
- 机器学习；
- TinyML。

这些内容都没有错，但它们被放在同一个平面上，容易造成一种错觉：

```text
好像所有知识都同样重要，
必须全部学完之后才能开始做底盘和 NN。
```

这不适合当前阶段。

你现在已经能够把以下内容组织成一个真实控制链：

```text
遥控输入
    ->
底盘速度指令
    ->
舵轮逆运动学
    ->
优劣弧调整
    ->
转向角度环
    ->
转向力矩环
    ->
驱动速度环
    ->
驱动力矩环
    ->
功率预测与分配
    ->
CAN 输出
```

所以，接下来的主要问题不是“还要不要再学一遍怎么写线程”，而是：

1. 这条控制链对应什么数学模型；
2. 每个采样周期内到底发生了什么；
3. 哪些数据可以用于辨识；
4. 当前模型在哪些工况下不成立；
5. NN 应该学习什么，而不是盲目替代什么；
6. 如何让 NN 即使出错，也不会把底盘推入危险状态。

新版路线的主线因此改成：

```text
数据可信
    ->
运动学正确
    ->
离散控制正确
    ->
模型辨识正确
    ->
传统控制器稳定
    ->
NN 学习一个明确的残差或调度量
    ->
PC 与 MCU 结果一致
    ->
影子运行
    ->
受限接管
    ->
实车验证
```

## 2. 当前底盘控制处在什么阶段

### 2.1 当前已经具备的控制能力

当前底盘线程已经不是简单的“遥控量乘一个系数再发给电机”。

当前控制周期约为 `1 ms`，主循环包含：

```text
ReadRemote()
    ->
UpdateTarget()
    ->
ControlCalculate()
    ->
PowerAlloc()
    ->
FramePublish()
```

当前已经具备的主要内容包括：

- 遥控器输入到底盘速度指令的映射；
- 两轮舵轮的逆向运动学；
- 舵轮角度归一化；
- 优劣弧判断；
- 转向角度环；
- 转向力矩环；
- 驱动速度环；
- 驱动力矩环；
- 电机状态快照读取；
- 功率预测；
- 功率预算分配；
- RLS 在线参数更新；
- CAN 发送帧组装；
- 固定周期控制循环。

这些内容已经足以支撑一条传统底盘控制链。

### 2.2 当前控制链的真实学习重点

当前最值得继续补的不是“再加一个 PID 功能”，而是下面这些问题：

| 当前问题 | 对应学习方向 |
| --- | --- |
| 运动学参数是否正确 | 机器人运动学和坐标系 |
| 控制周期是否稳定 | 实时系统和离散控制 |
| PID 参数为什么这样设置 | 控制理论和系统响应 |
| 功率模型是否可信 | 电机模型和实验辨识 |
| RLS 参数是否有物理意义 | 可辨识性和持续激励 |
| 数据是否适合训练 | 数据集设计和统计学习 |
| NN 应该输出什么 | 控制结构和学习目标设计 |
| NN 出错怎么办 | 安全约束、影子运行和回退 |

### 2.3 当前 NN 处在什么阶段

当前工程中已经存在 TFLM 的算法目录和一个基础推理线程，但它目前更接近：

```text
TFLM 运行时和模型接入验证
```

还不是：

```text
NN 已经接管底盘控制
```

当前底盘控制主链仍然是：

```text
串级 PID
    ->
功率预测与分配
    ->
电流输出
```

因此，当前 NN 学习路线必须明确：

> 先把传统控制链做成一个可信的基线，再让 NN 学习一个有边界、有标签、有评价标准的问题。

如果跳过基线，NN 很容易变成：

```text
数据不清楚
标签不清楚
模型不清楚
上板行为不清楚
最终也不知道效果好不好
```

## 3. 最重要的判断：NN 不是第一步

### 3.1 不要把 NN 当成更高级的 PID

NN 和 PID 解决问题的方式不同。

PID 依赖：

```text
误差
    ->
固定结构的反馈规律
        ->
控制输出
```

NN 依赖：

```text
输入特征
    ->
训练数据
        ->
损失函数
            ->
参数更新
                ->
推理输出
```

如果训练数据本身来自一个不稳定、未标定或错误的控制链，NN 只会把错误拟合得更复杂。

### 3.2 第一版 NN 不应该直接输出裸电流

对于当前底盘，第一版 NN 不建议直接输出：

```text
每个电机的最终电流
```

因为它绕过了太多已经存在的安全边界：

- 电流限幅；
- 电机方向；
- 功率预算；
- 速度上限；
- CAN 输出格式；
- 失联处理；
- 机械结构约束。

更稳妥的目标依次是：

#### 目标 A：学习 PID 残差

```text
u = u_pid + Δu_nn
```

其中：

```text
|Δu_nn| <= Δu_max
```

优点：

- PID 仍然提供基本稳定性；
- NN 只学习未建模部分；
- NN 输出可以很容易限幅；
- 训练标签可以从更好的控制器或实验数据获得。

#### 目标 B：学习增益调度

```text
kp_eff = kp_base + Δkp_nn
kd_eff = kd_base + Δkd_nn
```

优点：

- NN 不直接接触最终执行量；
- 可以给增益设置上下限；
- 更适合处理不同速度、负载和功率状态下的控制差异。

#### 目标 C：学习功率模型残差

```text
P_real = P_model + ΔP_nn
```

优点：

- 传统功率模型继续提供主解释；
- NN 只拟合摩擦、温度、非线性等难以建模的部分；
- 可以与现有 RLS 模型对比。

#### 目标 D：在仿真器中学习直接控制

只有在前面几个目标都完成、仿真和实车数据足够丰富后，才考虑让 NN 直接输出控制量。

### 3.3 推荐的目标顺序

```text
PID 残差
    ->
增益调度
    ->
功率模型残差
    ->
仿真中的直接控制
    ->
受约束的实车直接控制
```

不要反过来。

## 5. 第一阶段：建立可相信的数据链

### 建议时间

2 周。

### 阶段目标

在接触 NN 之前，先让底盘实验数据具备：

- 明确时间戳；
- 明确单位；
- 明确来源；
- 明确实验条件；
- 明确训练和验证边界。

### 5.1 需要采集什么

至少记录：

```text
时间戳
控制周期
遥控目标 vx
遥控目标 vy
遥控目标 vw
每个轮子的目标舵角
每个轮子的实际舵角
每个轮子的目标速度
每个轮子的实际速度
每个轮子的电流
每个轮子的转矩
每个轮子的 PID 误差
每个轮子的最终限幅电流
预测功率
实测功率
当前功率预算
控制模式
失联状态
```

如果某个量没有可靠来源，就不要在数据集里假装它存在。

### 5.2 每个数据字段必须有单位

推荐统一：

| 数据 | 单位 |
| --- | --- |
| 位置 | rad 或 m |
| 速度 | rad/s 或 m/s |
| 角速度 | rad/s |
| 电流 | A |
| 转矩 | N·m |
| 功率 | W |
| 时间 | s |
| 误差 | 与对应目标相同 |

训练数据中不要混用：

```text
rpm
rad/s
原始编码器值
```

除非每个字段名称和转换过程都被明确记录。

### 5.3 时间戳比日志行数更重要

控制数据必须能够回答：

```text
这个反馈是在目标产生之后多少时间到达的？
这个电流输出对应的是哪一帧反馈？
这一帧功率测量和哪一段控制行为对应？
```

建议每条数据至少包含：

```text
timestamp_us
sequence
source_timestamp
control_timestamp
```

### 5.4 先做数据质量检查

每次实验先检查：

- 时间戳是否单调；
- 是否存在重复时间戳；
- 是否存在大间隔；
- 是否存在 NaN；
- 是否存在明显饱和；
- 是否存在掉线；
- 是否存在传感器跳变；
- 是否存在单位错误；
- 是否存在方向符号错误。

### 5.5 本阶段练习

在独立 Python 工程中完成：

```text
日志读取
    ->
时间戳检查
    ->
单位转换
    ->
异常点标记
    ->
曲线绘制
    ->
实验报告
```

至少输出：

1. 目标速度和实际速度曲线；
2. 目标舵角和实际舵角曲线；
3. 电流和转矩曲线；
4. 预测功率和实测功率曲线；
5. 控制周期分布；
6. 丢帧和超时统计。

### 5.6 通过标准

你能明确回答：

- 一次实验从哪一时刻开始；
- 哪一段数据属于启动过渡；
- 哪一段数据属于稳态；
- 哪一段数据被饱和影响；
- 哪些样本不能进入训练集；
- 训练数据和验证数据如何按实验批次分开。

## 6. 第二阶段：补透底盘运动学

### 建议时间

3 周。

### 阶段目标

在学习控制器和 NN 之前，先确保“目标本身是对的”。

如果运动学错了，后面的 PID 和 NN 都可能只是拟合错误。

### 6.1 建立统一坐标系

必须明确：

```text
车体 x 轴方向
车体 y 轴方向
z 轴方向
正旋转方向
轮子编号
舵角正方向
电机反馈正方向
```

把这些内容写成一份独立的纸面说明，不要只留在代码注释里。

### 6.2 先做二维数学模型

对每个轮子，输入：

```text
vx
vy
vw
wheel_x
wheel_y
```

输出：

```text
wheel_velocity_x
wheel_velocity_y
wheel_speed
wheel_angle
```

先在 Python 中实现，不接电机。

### 6.3 验证四种基本运动

至少验证：

1. 纯向前；
2. 纯向右；
3. 纯旋转；
4. 平移和旋转叠加。

每种运动都要检查：

- 舵角方向；
- 行进速度方向；
- 两个轮子的相对关系；
- 旋转中心；
- 速度大小。

### 6.4 优劣弧必须单独验证

优劣弧不是一个简单的“角度大于 90 度就减去 pi”。

它需要验证：

```text
角度误差归一化
    ->
目标角翻转
    ->
行进速度反向
    ->
转向路径变短
```

需要测试：

- 误差接近 `0`；
- 误差接近 `pi/2`；
- 误差略大于 `pi/2`；
- 误差接近 `pi`；
- 从 `-pi` 跨越到 `pi`；
- 实际角度和目标角度符号相反。

### 6.5 运动学参数不要直接写死为真值

当前底盘中有一些机械参数仍然需要实测或进一步确认：

- 舵轮距离中心的半径；
- 轮子半径；
- 减速比；
- 舵向方向；
- 行进方向；
- 最大线速度；
- 最大角速度；
- 转矩常数。

学习任务不是记住这些数，而是建立：

```text
测量
    ->
记录
    ->
换算
    ->
验证
    ->
固定
```

### 6.6 本阶段练习

独立完成一个二维舵轮仿真器：

```text
输入车体速度
    ->
计算每轮目标
    ->
加入角度测量误差
    ->
执行优劣弧
    ->
输出轮子轨迹
```

加入以下扰动：

- 轮距误差；
- 轮半径误差；
- 舵角零点偏差；
- 方向符号错误；
- 角度噪声；
- 速度饱和。

### 6.7 通过标准

你能够不用看代码，解释：

- 为什么纯旋转时两个轮子的方向不同；
- 为什么目标舵角翻转后必须同步反转行进速度；
- 为什么角度必须归一化；
- 为什么机械参数误差会表现成控制误差；
- 哪些误差属于运动学，哪些属于电机控制。

## 7. 第三阶段：补透离散控制和串级 PID

### 建议时间

4 周。

### 阶段目标

把“PID 参数能工作”升级为：

```text
知道每一个环在控制什么
知道采样、延迟和限幅会怎样改变闭环
知道如何用实验判断问题来自哪一层
```

### 7.1 当前串级控制的学习顺序

当前每个轮子大致包含：

```text
转向：
    角度环 -> 力矩环 -> 电流

行进：
    速度环 -> 力矩环 -> 电流
```

不要一开始同时调全部参数。

推荐顺序：

```text
单电机电流/力矩响应
    ->
单电机速度环
    ->
单轮转向角度环
    ->
单轮转向和行进组合
    ->
整车运动学
    ->
功率约束
```

### 7.2 学习离散 PID

重点掌握：

- 连续 PID 到离散 PID；
- `dt` 的作用；
- 积分累积；
- 积分限幅；
- 积分分离；
- 变速积分；
- 微分先行；
- 微分滤波；
- 前馈；
- 输出限幅；
- 目标突变；
- 测量噪声。

当前 PID 实现中已经包含：

- 前馈；
- 死区；
- 变速积分；
- 积分分离；
- 微分先行；
- D 项低通；
- 输出限幅；
- 积分限幅；
- 参数影子切换。

学习时不要把这些功能当作“配置项列表”，而要为每一个功能建立独立实验。

### 7.3 每个 PID 功能对应一个实验

| 功能 | 实验问题 |
| --- | --- |
| 死区 | 小误差时是否减少抖动 |
| 积分限幅 | 饱和后是否仍然积累 |
| 积分分离 | 大误差时是否避免过冲 |
| 变速积分 | 接近目标时是否更稳定 |
| D 先行 | 目标突变时是否减少微分冲击 |
| D 低通 | 测量噪声是否被放大 |
| 前馈 | 目标变化时是否减少反馈负担 |
| 影子参数 | 调参切换时是否产生跳变 |

### 7.4 先用仿真理解，再用电机验证

每个功能都按以下顺序：

```text
Python 离散仿真
    ->
C++ 主机版本
    ->
单电机实验
    ->
底盘实验
```

仿真至少包含：

- 阶跃目标；
- 斜坡目标；
- 负载突变；
- 传感器噪声；
- 输出饱和；
- 采样抖动；
- 延迟。

### 7.5 串级 PID 的判断方法

调试时先问：

```text
外环输出是否合理？
内环是否跟得上外环？
电流是否被限幅？
反馈是否延迟？
机械方向是否正确？
```

不要一看到整车抖动就直接改最外层 `kp`。

### 7.6 本阶段练习

完成一个离散控制仿真器，包含：

```text

    ->
力矩环
    ->
速度环
    ->
角度环
    ->
限幅和功率约束
```

可以先只模拟一个轮子。

### 7.7 通过标准

你能够解释：

- 为什么外环和内环的带宽不能随意相同；
- 为什么采样周期改变后原参数不一定还能用；
- 为什么积分可能导致恢复慢；

## 8. 第四阶段：补透电机模型和功率控制

### 建议时间

4 周。

### 阶段目标

理解当前功率控制不是一个“附加限幅器”，而是一个带模型、辨识和分配策略的约束控制器。

### 8.1 当前功率模型

当前功率控制器使用的主要模型可以写成：

```text
P_in = K1 * τ² + K2 * ω² + τ * ω + K3
```

其中：

```text
K1 * τ²
    -> 与铜损相关的项

K2 * ω²
    -> 与转速相关的损耗项

τ * ω
    -> 机械功率项

K3
    -> 常数损耗项
```

学习时必须区分：

```text
模型表达式
    !=
真实物理定律的完整表达
```

它是当前控制场景下的近似模型，需要通过实验确认有效范围。

### 8.2 当前功率控制的主要步骤

当前 PowerCtrl 主要完成：

```text
SetMotorData()
    ->
计算 τ、ω、τ²、ω²
    ->
Predict()
    ->
功率预测与 RLS 更新
    ->
Allocate()
    ->
按误差和预测功率分配预算
    ->
求解受限电流
```

因此你需要学习四类知识：

1. 电机功率和转矩的物理关系；
2. 模型参数如何辨识；
3. 约束下如何分配预算；
4. 限幅后闭环如何变化。

### 8.3 功率分配不是简单平均

当前分配同时考虑：

- PID 误差；
- 预测功率；
- 总功率预算；
- 转向组优先级；
- 行进组剩余预算；
- 单电机受限电流。

这意味着功率限制和控制器之间存在耦合：

```text
控制误差大
    -> 更希望获得功率

预测功率高
    -> 更需要被限制

转向优先
    -> 行进可用预算变化
```

学习时要把它看成一个受约束控制问题，而不是一个独立的数学小工具。

### 8.4 功率控制实验

至少完成下面四组实验：

#### 实验 A：无功率限制

验证：

```text
PID 目标电流
    ->
最终输出电流
```

是否一致。

#### 实验 B：固定功率预算

逐步降低预算，观察：

- 速度响应；
- 角度响应；
- 电流削减；
- 误差积累；
- 恢复过程。

#### 实验 C：误差权重变化

改变 `errLower` 和 `errUpper`，观察：

- 误差大的电机是否得到更多预算；
- 预测功率大的电机是否仍然被压制；
- 权重变化是否连续。

#### 实验 D：转向和行进组优先级

改变转向组预算比例，观察：

- 转向稳定性；
- 行进速度；
- 整车方向误差；
- 功率利用率。

### 8.5 通过标准

你能够解释：

- 为什么功率预算会改变底盘闭环；
- 为什么转向和行进不能简单使用同一套权重；
- 为什么总预测功率没有超限时可以直通；
- 为什么超限时要解受限转矩；
- 为什么受限输出可能使积分策略需要重新考虑。

## 9. 第五阶段：正确学习系统辨识

### 建议时间

5 周。

### 阶段目标

让 RLS 和系统辨识从“会调用”变成：

```text
知道辨识对象

知道参数是否有物理意义
知道什么时候不能相信结果
```

### 9.1 先区分三个概念

必须区分：

```text
数据拟合
    -> 能把曲线拟合得像

系统辨识
    -> 用数据估计模型参数

物理建模
    -> 参数具有明确物理解释和适用范围
```

一个模型拟合得好，不代表它就是一个可靠的物理模型。

### 9.2 当前 RLS 的学习重点

当前功率控制中的 RLS 主要围绕：

```text
K1
K2
```

进行在线更新。

你需要掌握：

- 回归向量；
- 目标值；
- 遗忘因子；
- 初始协方差；
- 参数初始化；
- 持续激励；
- 输入共线；
- 噪声；
- 参数漂移；
- 条件数；
- 复位和冻结。

### 9.3 为什么当前空载开环实验不能直接当全局模型

当前仓库已经记录过一个重要结论：

```text
空载、纯转矩、长时间平台激励
```

不适合直接拿来拟合全局 `torque -> omega` 传递函数。

原因包括：

- 空载下没有理想稳态；
- 非零转矩可能让电机持续加速；
- 数据大量集中在速度上限附近；
- 输入和方向项可能高度相关；
- RLS 只能拟合当前工况的现象；
- 最终参数未必具有全局物理意义。

这不是 RLS 算法本身失效，而是实验条件没有提供足够好的辨识信息。

### 9.4 重新设计辨识实验

推荐从以下实验开始：

#### 小信号阶跃

在稳定工作点附近施加小扰动，观察局部响应。

适合估计：

- 局部增益；
- 局部时间常数；
- 局部延迟。

#### PRBS

使用伪随机二进制序列激励，避免输入过于单一。

#### 多正弦

使用多个频率成分，观察不同频段的响应。

#### 闭环辨识

在稳定控制器外面加入小扰动，而不是完全取消反馈。

#### 多工况辨识

分别采集：

- 低速；
- 中速；
- 高速；
- 空载；
- 轻载；
- 不同温度；
- 不同功率预算。

### 9.5 数据集切分不能按随机行切

控制数据存在时间相关性。

不能简单地把连续数据随机打散为训练集和验证集，否则相邻样本可能同时出现在两边，导致验证结果虚高。

推荐按实验批次切分：

```text
实验 1、2、3
    -> 训练集

实验 4
    -> 验证集

实验 5
    -> 测试集
```

### 9.6 通过标准

你能够回答：

- 当前 RLS 的输入向量是什么；
- 目标值是什么；
- 哪些参数可以同时被辨识；
- 哪些实验工况导致输入共线；
- 遗忘因子变大或变小会带来什么影响；
- 什么数据不能拿来训练；
- 为什么一个漂亮的拟合曲线可能仍然没有物理意义。

## 12. 第八阶段：让 NN 安全进入控制链

### 建议时间

5 周。

### 阶段目标

不追求“让 NN 取代 PID”，而是建立一个可回退、可比较、可停止的接入流程。

### 12.1 第一步：离线回放

使用历史实验数据，让：

```text
传统控制器
    ->
NN 控制器
```

在完全相同的输入下运行。

比较：

- 跟踪误差；
- 峰值误差；
- 稳态误差；
- 输出抖动；
- 输出能量；
- 功率使用；
- 超限次数。

### 12.2 第二步：影子模式

影子模式下：

```text
PID 输出
    -> 真正发送

NN 输出
    -> 只计算、只记录、不发送
```

需要记录：

- PID 输出；
- NN 输出；
- 两者差值；
- 当前工况；
- 推理时间；
- 模型是否触发限幅；
- 当前功率状态。

### 12.3 第三步：残差限幅

第一版接入建议：

```text
u_final = clamp(u_pid + Δu_nn,
                u_min,
                u_max)
```

同时限制：

```text
|Δu_nn| <= delta_max
```

`delta_max` 不应该由 NN 自己决定。

### 12.4 第四步：门控接管

只有满足以下条件时才允许 NN 参与：

- 传感器在线；
- 数据没有超时；
- 输入在训练分布内；
- 推理耗时未超限；
- 输出没有 NaN；
- 输出没有超过限制；
- 控制误差没有连续恶化；
- 功率状态正常。

否则：

```text
立即回退到基线 PID
```

### 12.5 第五步：逐步扩大工作范围

推荐顺序：

```text
单轮仿真
    ->
单轮离线回放
    ->
单轮影子运行
    ->
单轮小幅度残差接入
    ->
低速整车
    ->
中速整车
    ->
受限功率整车
```

不要直接从训练好的模型跳到高速实车。

### 12.6 NN 的停止条件

以下任一情况出现时，停止 NN 接管：

- 输出出现 NaN；
- 推理超时；
- 输入超出训练范围；
- 控制误差连续扩大；
- 功率超限；
- 电机反馈丢失；
- 传感器状态不可信；
- 模型输出频繁触发限幅；
- 实验结果明显不如基线。

### 12.7 通过标准

你能够完成：

```text
基线 PID
    ->
NN 影子输出
    ->
残差限幅
    ->
故障回退
    ->
离线和实车对照
```

并且可以用数据回答：

- NN 到底改善了什么；
- 改善是否稳定；
- 哪些工况下反而变差；
- 增加了多少计算成本；
- 是否值得继续接管。

- 推理超时；
- 模型版本不匹配。

### 13.6 实车测试记录

每次实车测试至少记录：

```text
硬件版本
软件 commit
模型版本
训练数据版本
控制参数
功率预算
实验环境
实验目的
实验结果
异常情况
是否允许继续扩大范围
```

### 13.7 通过标准

至少做到：

```text
每个新控制功能都有离线测试
每个模型都有 PC 与 MCU 对照
每次实车实验都有版本记录
每次异常都有回放数据
```

## 14. 当前阶段不应该做什么

### 14.1 不要先让 NN 替换整个 PID

先做：

```text
残差
    ->
增益调度
    ->
模型残差
```

再考虑更强接管。

### 14.2 不要用错误工况训练复杂模型

如果实验已经被：

- 速度上限；
- 电流限幅；
- 功率限幅；
- 传感器饱和；
- 失联；
- 机械卡滞；

主导，就不要直接把这些数据当成理想控制标签。

### 14.3 不要只看训练误差

必须看：

- 验证误差；
- 未见工况；
- 时间连续性；
- 输出抖动；
- 控制稳定性；
- 功率消耗；
- 推理成本。

### 14.4 不要创建不存在的训练脚本作为计划前提

当前仓库已经有多类 IMU 实验脚本，但底盘 NN 训练流程还没有形成一个固定的 `train_pid.py` 主线。

所以正确的学习顺序是：

```text
先建立底盘数据格式和独立训练脚本
    ->
再确定模型任务
    ->
再接 TFLM
```

不要把“计划中的训练脚本”写成“当前已经存在的工具”。

### 14.5 不要把 TFLM 目录等同于 NN 控制已经完成

当前 TFLM 相关代码可以先用于：

- 模型加载；
- 推理流程；
- arena；
- 算子；
- PC/MCU 对照；
- 推理耗时。

但底盘闭环接入仍然需要独立完成：

- 数据集；
- 标签；
- 基线；
- 影子模式；
- 输出限制；
- 回退策略；
- 实车验证。

## 16. 比赛期间和赛后如何安排

### 16.1 比赛期间

比赛期间不要进行大规模 NN 接管，也不要因为学习计划去修改稳定控制链。

比赛期间适合做：

- 数据采集；
- 日志格式整理；
- 离线回放；
- 运动学仿真；
- PID 参数记录；
- 功率数据记录；
- 影子计算但不接管；
- 独立 Python 实验。

比赛期间不适合做：

- 直接替换底盘 PID；
- 直接引入未经验证的模型；
- 修改多个控制环；
- 更换功率分配策略；
- 在实车上同时验证多个变量。

### 16.2 赛后第一阶段

赛后先做：

```text
数据整理
    ->
基线复现
    ->
实验分组
    ->
模型训练
    ->
离线评估
```

不要刚结束比赛就立刻重写控制链。

### 16.3 赛后第二阶段

再做：

- TFLM 推理；
- 影子模式；
- 低速接入；
- 单轮验证；
- 小范围残差控制；
- 系统化回归。

### 16.4 赛后第三阶段

只有在结果稳定后，再考虑：

- 更大的训练集；

## 19. 最终路线总结

当前最合理的学习路线不是：

```text
先学完所有芯片
    ->
再学完所有 RTOS
    ->
再学完所有控制
    ->
最后学 NN
```

更适合你的路线是：

```text
先把底盘数据记录清楚
    ->
补透运动学
    ->
补透离散控制
    ->
补透功率模型
    ->
正确进行系统辨识
    ->
用小型回归任务学习 NN
    ->
完成 PC 与 MCU 一致性
    ->
影子运行
    ->
残差限幅接入
    ->
实车验证
```

对应的优先级是：

```text
第一优先级：
    数据、运动学、离散控制

第二优先级：
    电机模型、功率控制、RLS、实验设计

第三优先级：
    回归、数据集、模型评估、量化

第四优先级：
    TFLM 部署、影子模式、受限接管
```

最后要记住：

> NN 不是底盘控制的起点，而是建立在数据、模型、控制器和验证体系之上的一个可选增强模块。

你真正要学会的，不是“如何把神经网络塞进底盘”，而是：

```text
如何提出一个可验证的问题
    ->
如何采集能够回答这个问题的数据
    ->
如何建立可信的基线
    ->
如何让模型只承担它应该承担的部分
    ->
如何在模型失败时安全退出
```

当这条链路能够独立完成时，NN 才真正成为控制能力，而不是一个挂在工程里的推理 Demo。
